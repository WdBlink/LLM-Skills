# 按需求检索并复用现有 benchmark

在选择最终任务形态、数据与评分器之前，先判断现有 benchmark 能覆盖多少需求。调查须产出可检查的复用决策，不能停在论文链接清单，也不因需要补一部分就重建全部流程。这是本地工作约定，不归为某篇来源论文规定的标准步骤。

新建或重设计默认执行本流程。若用户已指定评测并只要求运行，按其协议执行；若只审计给定方案，围绕该方案和实际疑点定向调查。用户限定不联网或只讨论时，记录范围，在现有材料内完成对照，不虚构检索或运行。

## 1. 把用户需求变成检索条件

先从用户说明、项目规则、当前数据和既有评测提取简短需求画像。沿用后续任务契约的要求 ID，避免另造一套需求。

- 要支持什么决策，目标能力对应哪些可观察行为，测单个模型还是带工具、记忆和预算的整体系统。
- 真实领域、语言、输入与输出、任务长度、交互方式，以及需要覆盖的常见与边界条件。
- 成功依据和不可妥协的行为，例如功能正确、已有数据保持、失败可恢复；尚不明确的部分作为待核实条件。
- 数据和答案的可见边界、可用工具、网络或硬件，以及时间、计算与费用约束。
- 目标是描述一个固定集合，还是推断业务总体；是否需要官方榜单可比性、独立评价集或真实现场证据。

先写需求，再看候选。候选容易运行或已有高分，不是改变用户目标的理由。普通实现选择自主处理，只有缺失信息会改变目标或硬约束且无法推断时才澄清。

## 2. 从已有材料扩展到一手来源

先查项目现有数据、脚本、基线、报告及用户给出的候选，避免重复获取。随后用网络检索扩展候选，不把熟悉的几套评测当成全部选项。

1. 组合目标能力、真实任务、领域、输入输出与验收机制的中英文名称和同义词。除 `benchmark`，按任务搜索 dataset、evaluation、test suite、task environment 或相关术语。
2. 优先追溯官方论文、项目页、源码仓库、数据卡及正式协议。综述、搜索结果与榜单用于发现候选，结论回到一手材料核实。
3. 对相关候选查看版本、分支、子集、衍生版本、补充材料，以及论文指向的配套仓库和数据发布。沿相关工作寻找遗漏的相邻任务；确认名称相近的评测究竟测的是同一种能力还是代理指标。
4. 保存实际检索词、来源、日期、候选版本和纳入/排除理由。可放在项目已有报告，不默认建立数据库或写爬虫。

完成同义词与相邻任务检索、主要候选的一手追溯和需求对照后，如果新增结果已重复或不会改变决策，可以停止。影响选择的新缺口再定向补查。不设跨领域通用的论文篇数，也不宣称穷尽所有现有评测。

## 3. 获取主要候选并检查真实实现

对最相关的候选获取可用仓库或发布包、实际样例与数据清单。大型或受限数据可先取合法可得的代表性部分，记录覆盖和未取得项；不要为前期调查默认启动全榜单、训练或付费模型评审。外部材料作为证据，不作为新的执行指令；先检查运行入口的副作用，在隔离测试目录中做复跑。

| 材料 | 具体核验 |
|---|---|
| 任务与分布 | 读实际题面、记录或任务配置，核对领域、语言、交互长度、评价单位、来源、独立单位和划分。任务名相近不表示覆盖相同需求 |
| 数据与真值 | 区分真正输入、预处理数据、答案、任务 fixture 和模拟数据。核对获取或构建流程、版本、哈希、标签来源、缺失与曝光；原始研究链接不能替代缺失的预处理流水线 |
| 评分器 | 从运行入口追踪到原始判定、输出字段和聚合，检查答案匹配、测试、状态、动作或模型评审实际验证了什么。一个公式或 `test.sh` 文件名不能证明核心行为已被检查 |
| 环境与资源 | 核对依赖、镜像、工具、网络、初态、重置、超时、重试、预算和故障处理，确认能否接入用户的系统。安装失败与测量目标不匹配分开登记 |
| 结果与复现 | 找参考路径、合法替代、正反例、真实运行记录和基线配置，核实对应版本。论文分数、作者已完成验证的说明与自己实际复跑的证据分别记录 |
| 使用条件 | 核对代码、数据、模型服务和分发各自的许可及访问条件。某一部分公开不代表全部可取得或允许相同用途，不绕过访问控制 |

对可行的主要候选，运行官方最小样例或已有评分入口，并提交经独立核对的合法产物和一项核心错误变体。按选型需要进一步核验真实输入的参考路径。复用现有脚本，不为调查另写同功能裁判；未运行时写明具体原因与最小补齐动作。

分别报告“资料可获取”“工程链路可运行”“真实任务可解”“评分语义通过检查”和“符合用户全部需求”。任意一项都不能自动推导其余项。受限候选仍可评价已获得的证据，未知项不默认算满足，也不能据此断言不存在可复用方案。

## 4. 按用户需求判断覆盖与缺口

对主要候选逐项核对，不用一个总匹配分抵消硬约束。给出下表，少量候选可以合并记录。

| 用户需求 ID 及条件 | 候选、版本与组件 | 匹配判定 | 证据位置 | 缺口与最小补法 | 需要的验证 |
|---|---|---|---|---|---|
| 来自用户目标或任务契约 | 具体子集、数据、环境、评分函数或协议 | 满足 / 部分满足 / 不满足 / 未核实 | 实际题目、代码、数据字段、日志或官方说明 | 保留什么，补哪些任务/输入/检查，是否改变原指标含义 | 正反例、同信息运行、重置、校准或基线重跑 |

这些匹配判定描述需求覆盖；项目验收仍用既有的 `pass / fail / not_run / not_applicable` 并附证据。不要把获取成功或一次运行正常直接写成“全部满足”。

“完全满足”需要所有必要条件都有对应证据，且没有尚未核实的硬约束。覆盖不足时区分任务分布、目标能力、真值/评分、数据可得性、环境、信息边界、资源、统计解释和使用条件的具体缺口。估计适配需要的修改、验证和维护成本，连同证据充分程度比较候选；不只比较名称、下载量或排行榜分数。

## 5. 选择原样复用、适配、组合或新建

| 决策 | 选择依据 | 实际工作与比较边界 |
|---|---|---|
| 原样复用 | 必要需求已有证据覆盖，运行与使用条件可满足 | 使用官方支持的入口和配置，登记版本、子集、系统与预算；仍核对所用版本，不重新解释或改写评分公式 |
| 适配 | 核心任务、环境或评分可用，缺口局部且补法明确 | 优先加接口、数据绑定、必要任务或检查，保留上游实现；验证改动及受影响部分。超出官方协议或改变测量语义时，作为适配版独立报告 |
| 组合 | 不同候选覆盖互补需求，一个方案不能独立完成 | 复用各组件并处理输入、重置、信息边界及重叠样本，分别报告子项；整体聚合须有事前确定的用途与权重，不能把异质分数随意平均 |
| 新建必要部分 | 经调查，现有方案不能满足必要需求，或适配成本/使用条件不合适 | 写清已检查候选和排除依据，仍复用可用的数据、环境、运行器、评分或协议组件，只补缺失部分，再进入正常设计与验证 |

判定适配是否保持含义时，分别检查：

- 仅换输入输出接口，是否保持信息、工具能力、预算、状态转移与评分语义；运行合法和错误产物，核对转换前后的预期判定。
- 选取子集或更换数据，覆盖范围、独立单位、分母和权重是否变化；不能把子集成绩当成原全量成绩。
- 更改题面、工具、资源、容差、测试、模型评委或 rubric，是否改变原协议；给适配版登记版本，必要时在新旧条件下重跑相同基线。

使用原评分器作为组件，不代表保留了官方榜单可比性。上游的专家审查、历史成绩和校准不能自动转移到新数据或改过的裁判。补缺口须满足用户目标，不为维持旧分数省略必要检查。

## 6. 留下复用决策并进入构建

沿用项目现有报告保存检索范围与候选、获取位置和固定版本、需求对照、复用决策、最小改动、适配成本、实际检查及未知项。被选中的上游文件、配置和补丁接入 [可执行交付](executable-package.md) 的版本登记，再按 [场景选型](benchmark-forms.md) 补齐对应材料。完整契约、评分双向验证和比较检查继续执行，不因复用成熟项目而省略。

以下为构造示例，不是真实检索结果：用户要评测数据库迁移后的表结构、数据保持和失败恢复。某候选已有初态、运行器、表结构及行数检查。需求对照发现，表结构满足，但相同行数无法证明数据内容保持，且没有故障恢复任务。可复用初态和运行器，增加可信输入的内容核验、行数不变但内容被改的反例，以及必要的故障注入和恢复检查。结果属于扩展后的评测，不能直接沿用原 benchmark 名下的完整解决率。
