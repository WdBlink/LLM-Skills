# 结果验收与返工

本节是本地执行约定。新建或重设计 benchmark 时，把最终验收当成必经阶段；文件写完、生产者自报完成或一次 smoke test 都不能终止构建。先运行项目已有、覆盖下述四项的验收入口；缺少时使用本技能的 `scripts/accept_benchmark.py`，适用范围见后文。不要只调用文件哈希检查器，也不要为验收另写一套领域评分公式。

## 先冻结验收合同

在查看正式比较结果前，按任务契约确定评价集/实际实例、预计数量和纳入条件、指标及聚合、代表性方法及其版本/配置、主要方法对、共同信息和资源预算、故障/缺失分母，以及对用途有意义的差异标准。需要推断或随机比较时，另定独立单位、配对/重复和不确定性方法。阈值来自用途与计分分辨率，不能为让现有结果过关事后降低。

“至少两个现有方法”是取得方法间区分证据的最低结构要求，不是充分样本量。方法须与用户的比较目标相关；参考正确解、故意错误解、fake judge 和裁判 fixture 用来测可解性或评分正确性，不能冒充现有方法基线。方法的真实运行记录、预测/产物与正式数据版本相连；仅有名称或引用论文中的异版本分数不算本次比较。

## 固定的四项验收

| 检查 | 实际执行与必存结果 | 不通过后的责任位置 |
|---|---|---|
| A1 数据集确实形成 | 解析实际实例清单，核对稳定 ID、来源/性质/角色、切分、数量、重复和输入/初态/附件能否取得；保存实际数据或受控快照、清单和版本。生成器/环境/现场协议还须保存这轮产生的实例与初态，只有链接、生成代码或几条裁判 fixture 不算评价集完成 | 回到数据获取/构建和任务契约；不改成只检查文件数量 |
| A2 脚本针对数据可运行 | 从干净或可恢复初态，实际调用保存的准备/运行/评分入口，记录完整命令、工作目录、环境、版本、返回码、超时与诊断。核对评分器确实消费该评价集和方法产物；需要的脚本逐一执行，不能只测 `--help` 或语法。可复用已有冻结方法产物，重评分不能冒称重新运行方法 | 修相应输入、依赖、调用、重置或共享 harness；保留无关的有效产物 |
| A3 得分明确且可复算 | 从实际产物取得逐评价单位、逐指标的原始判定与分数，检查缺失/重复/越界/非有限值、全量覆盖、失败分母和方向；按权威实现复算汇总，与保存报告对照。保留总分、子组/指标明细、配置及校准/正反例检查；只打印 `pass`、硬编码得分或仅有不明来源总分不算通过 | 修评分器、输出适配或聚合；同步回归误收/误拒，不悄悄丢掉失败样本 |
| A4 区分能力有实测 | 在相同正式实例、信息和比较预算上取得至少两个相关现有方法的结果；报告各方法分数、主要配对分差、逐项胜/平/负及适用的地板/天花板/分组现象。按冻结的比较协议检查差异的实际意义，以及随机性/独立单位/不确定性是否支持所声称的区分；不能只说“有区分度” | 补跑缺失方法/重复，或诊断覆盖、计分灵敏度、噪声及基线是否适当；有理由修改时新建版本并重跑受影响比较 |

数据集不必是公开的静态问答表；私有数据可在授权环境内验收，报告不泄露答案。主观任务可以让人或模型按 rubric 产生原始标签，再用保存的程序计算分数；程序运行成功不证明语义裁判正确，仍须校准和实际审阅。用户明确只要质性设计时按该范围交付，不能称已完成可计分 benchmark。

区分度为零也是实测结果。若目标是系统排名或选择，未达到事先标准就不能把它验收为可用的排名 benchmark；也不能据此直接宣称方法相等或评分器无效。若原定目标是覆盖/回归，允许观察到同分，但须事先写明无需拉开排名的理由，并交付实际测得的差异。不能看见失败后改口称只测覆盖。

## 验收结果决定下一步

在项目已有报告中按 A1–A4 分别写 `pass / fail / not_run`、证据位置、失败原因、责任步骤和下一动作；四项不能互相抵消，不能用 `not_applicable` 跳过本次构建的必要结果。

```text
构建/试跑 → 固定四项验收 → 全部满足 + 契约/评分/比较有效性审阅通过 → done
                         → 可在当前授权内修复 → needs_work → 定位修复 → 重验受影响项
                         → 缺外部必需输入/资源 → needs_input，保留未完成与解除条件
```

`needs_work` 要继续执行补建、修复与重验，不能只是最终答案列一张 TODO 就结束。补丁改变数据/评分/预算/比较条件时，相关旧成绩和审阅失效；未变的输入、方法产物和独立成功步骤继续复用。重新验收必须绑定当前版本，不读取历史 `passed` 就放行。

外部权限/数据/资源缺失、约定预算耗尽或关键假设被否定时可以停止本轮执行，但状态必须是未完成，并说明已有结果与最小补齐动作。禁止伪造日志、把构造演练当真实区分证据、反复调题直到出现预期名次，或擅自扩大付费/API/发布范围。纯审计可完整交付“不合格”的审计结论；这不使被审 benchmark 变为完成。

四项实测还须与主流程的目标覆盖、可解性、评分双向正确、信息边界和比较公平性审阅合并判断。AI 可核查程序和准备意见，不能冒称有人类专家确认；缺少必要真人复核时保留 `human_review_pending`，只交付候选及已验证范围。

## 已提供的程序入口

`scripts/accept_benchmark.py` 使用 Python 3.9+ 标准库，适合**同一固定集合、逐单位配对、以 mean 或 sum 聚合的数值指标**。它读取项目产物和现有领域评分器，执行评分、检查完整覆盖、独立聚合，再计算各指标分数范围、全部方法对的分差/胜平负及已声明边界上的占比。是否达到区分要求只看**预先指定的主要方法对**，不能用某个极弱方法拉大的全局范围代替主要比较。

非可分解指标、加权/分层聚合、随机系统排名、总体推断、不配对任务等，调用项目权威入口实现同样四项验收，并保存相应统计证据；项目没有该入口时补齐最小领域适配/统计检查，验证后执行同样的验收与返工。不要为套用此工具改变官方口径。此工具只给固定集合描述，输出 `uncertainty: not_assessed`，不计算显著性或把相关单位当独立样本。多次运行和子组结果按正式协议补充，不能以工具返回 `0` 代替这些证据。

准备以下小型 JSON 合同，沿用已有目录；示例字段对应真实路径与语义，不能原样当作本次已完成记录：

```json
{
  "schema_version": 1,
  "registration": "registration.json",
  "data_role": "evaluation",
  "dataset_manifest": "instances.jsonl",
  "expected_units": 120,
  "scorer": "score.py",
  "score_argv": ["python3", "{scorer}", "--dataset", "{dataset}", "--predictions", "{predictions}"],
  "timeout_seconds": 60,
  "metrics": [
    {"id": "success", "score_basis": "任务契约中的目标与保留条件", "aggregation": "mean", "direction": "higher", "min": 0, "max": 1}
  ],
  "methods": [
    {"id": "method-a", "kind": "existing_method", "description": "实际版本、配置与选择依据", "predictions": "runs/a/output.jsonl", "run_evidence": "runs/a/run.json"},
    {"id": "method-b", "kind": "existing_method", "description": "实际版本、配置与选择依据", "predictions": "runs/b/output.jsonl", "run_evidence": "runs/b/run.json"}
  ],
  "discrimination": {
    "scope": "fixed_set_descriptive",
    "metric": "success",
    "pairs": [["method-a", "method-b"]],
    "min_gap": 0.05,
    "unit_tie_tolerance": 0,
    "require_separation": true,
    "rationale": "根据本次用途事先确定该分差有实际意义"
  }
}
```

这里的数量、超时和分差只展示格式，不是默认门槛。`min/max` 是可选的逐单位分数边界；方向为 `higher/lower`。`min_gap` 必须为正，按聚合后的主要指标尺度解释，所有主要方法对均须达到；`unit_tie_tolerance` 按该指标的逐单位尺度解释。其他指标仍报告观察值，但不自动代替主要指标。`require_separation: false` 只适用于事先约定的非排名用途，仍需两种方法的实测和明确理由，不表示已经具备排名区分能力。

`instances.jsonl` 每行只需为原数据建立索引，不要求转换原始任务格式：

```json
{"id":"task-001","files":["tasks/task-001/input.json","tasks/task-001/initial-state.json"]}
```

`files` 非空且指向实际实例材料，清单 ID 唯一、数量与冻结合同一致；合法空输入文件可以是边界实例，其内容有效性仍需领域审阅。`registration.json` 使用 [文件登记格式](executable-package.md#可选的文件完整性入口)，登记验收合同、实例清单、全部附件、配置/依赖锁、评分器及其导入模块、方法产物和运行证据。大型/受控数据优先用项目验证器，不为此脚本复制秘密。路径按产物根目录解释，登记不能随意改哈希延续旧版结果。

领域评分器或薄适配器须读取清单和当前方法产物，stdout 输出 JSON，诊断写 stderr：

```json
{"scores":[{"unit_id":"task-001","metrics":{"success":1}}]}
```

输出必须覆盖该方法的所有评价单位和声明指标；顺序可变，未知/重复/缺失 ID、非数值、布尔值和非有限数均拒绝。方法能力失败按原协议给出分数和原因，基础设施故障另行处理，不能靠删行改善分母。保留原始判定与来源证据，适配器只转换输出，不另造算法。`run_evidence` 内容及方法身份、信息/预算公平性、源判定和指标语义由审阅者实际核对，程序不会因一个自报字段就证明其真实。

```sh
python3 /absolute/path/to/good-benchmarks/scripts/accept_benchmark.py \
  /absolute/path/to/benchmark/acceptance.json \
  --report /absolute/path/to/run/acceptance-result.json
```

默认根目录为合同目录；分离时传 `--root`。入口不依赖工作目录，使用参数数组、明确 cwd 和超时执行命令，不用 shell；`{scorer}/{dataset}/{predictions}/{root}` 替换为实际路径。验收合同中的命令仍是要事先核对的可执行代码，不自动执行外部下载包的指令，也不自动启动方法生成、付费裁判或服务。

报告保存输入版本/哈希、四项状态/下一动作、实际命令/返回码/耗时/stdout/stderr、重新聚合的分数及区分明细。评分前后检查冻结产物未被更改。`--report` 必须是新文件，避免覆盖输入和历史证据。返回 `0` 表示 `execution_checks_passed`，只证明这四项的**程序可核对部分**通过；`semantic_validity: not_assessed` 明确不代替领域有效性与专家复核。返回 `1` 表示 `needs_work` 并定位失败，未到达的项为 `not_run`；参数/报告路径冲突返回 `2`。修复后用新报告重跑，复用未变的方法产物，不为重评分重新求解。
