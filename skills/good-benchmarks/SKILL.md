# Good Benchmarks

把用户真正需要区分的能力变成有证据的评测。依据 Ivan Bercovich 的 [Good Benchmarks, v1](https://arxiv.org/html/2607.12217v1)；这是 Terminal-Bench 实践方法的本地实现，不宣称存在适合所有任务的“最佳 benchmark”。来源位置和适配边界见 [source-notes.md](references/source-notes.md)。

## 原则与加载

原文核心：任务来自真实工作；目标充分明确；可在约定资源内解决；验证器接受正确结果并拒绝错误结果；难点属于目标能力；环境稳定；专家审阅实际解题过程。低通过率本身不能证明 benchmark 有价值。

下述执行流程、契约、测试矩阵与跨领域例子为本地工程化设计。开始设计时读 [任务契约](references/task-contract.md)；按问题选读 [案例](references/examples.md)，同时看反例。纯审计聚焦已有题面、环境、评分器、日志及相关契约，不另造平行框架。

## 执行流程

1. **确定要支持的判断。** 读取当前项目规则与已有评测；确认使用者、真实工作场景、目标能力、比较对象和预期用途。用一句话说明“这个结果能支持什么决策”，另记不覆盖的能力。缺少会改变目标的输入才询问；已有范围内继续准备。
2. **建立任务契约。** 按参考文件记录输入、可访问资源、输出语义、允许变化、资源预算和成功条件。给每项要求一个 ID，并映射到检查及证据。区分提供给被测系统的任务信息与仅供评测方使用的答案、测试和诊断记录；隐藏测试不意味着隐藏成功标准。
3. **选择评价方式。** 可程序判定的目标采用确定性语义检查；随机或统计目标预先定义估计量、重复方式和不确定性；涉及偏好时分离客观底线与人工评价。若无法形成可解释的判定，保留探索性研究身份，不用一个 LLM 分数伪装为客观正确率。不要为了方便评分偷换用户目标。
4. **先做最小可解样例。** 在被测系统的实际权限、输入和预算内运行一条有依据的参考路径，保存产物、日志和资源用量。参考解作者可以知道答案，执行过程却必须能从提供的信息重建结果；持有答案的评分器与不应获答案的求解器分开。只有论证而未运行时标记 `solvability_argued`，不能称端到端通过。
5. **独立检验评分器。** 从契约导出正例、另一种合法解、边界及错误变体；参考 [任务契约的验证矩阵](references/task-contract.md#验证矩阵)。使用项目现有测试设施。既测误接收也测误拒绝，并区分候选答案失败、评分器故障和环境故障。修复共享 harness 问题时回归所有受影响任务。
6. **试跑并解释失败。** 冻结一个候选版本，记录每次被测运行的模型/系统版本、预算、输入、输出、轨迹、评分和成本。失败归类为能力、题面、环境、评分器或未确定；检查实际失败点是否对应预设难点。提示实验、换合法实现和资源检查用于定位原因，不能把得到提示的成绩混入正式结果。
7. **形成集合与比较协议。** 多任务集合增加覆盖维度、抽样依据、分组、去重、开发/评价隔离和聚合方式。提前确定失败分母、重试与基础设施故障处理；同时报告分组结果和重复运行的不确定性，不能只挑最好一次。任务版本、数据或评分改变后分开报告，必要时重跑可比基线。单项测试不硬凑任务数量或宏大榜单。
8. **审阅与交付。** 让能解决该领域问题的人核对题意和有效性，让了解评测的人核对信息边界和评分漏洞；同一人兼具能力即可。AI 可准备证据和审阅候选意见，但不得冒称已有人类专家确认。缺少专家时仍完成可做的构建与试跑，交付已验证范围并标 `human_review_pending`。既有用户审阅可作为实际记录，无需为每次编辑重复批准。

## 决策边界

- 不以删必要信息、制造格式陷阱、拼接无关小任务或事后压低预算来追求低通过率。若格式、时延、长程协调本来就是工作要求，可评测它们，但须解释其现实依据并单列归因；不得称其测量了另一种能力。
- 不照着参考实现检查库名、源代码字符串或工具轨迹。只有任务明确要求的接口、真实流程义务或防作弊边界才限制过程，并说明理由；其余合法实现按结果验收。
- 不把“加提示后通过”当作普遍公平的证明；它只帮助区分给定方法下的可解性与原任务的能力要求。对争议领域常识核对权威资料；说明必要假设，保留真正需要推理的部分。
- 固定资源、依赖和数据，保存可重建的版本/哈希。必须联网或接真实硬件的任务另行记录时间、服务/设备状态和配对比较条件；能冻结回放的部分先冻结，剩余漂移单独披露。不得把环境失效悄悄算成模型能力失败。
- 从评分输出、答案文件、可写测试、挂载目录、缓存、网络和重置边界检查绕过路径。攻击测试只在获授权的隔离评测环境中进行；修复后同时重放攻击与正常解，防止封堵使合法任务不可解。
- 小改动导致大幅成绩变化、失败集中于相同答案、反复评审不收敛或成本异常，先检查具体证据。这些是诊断信号，不能单凭其中一项宣布模型差、任务无效或存在作弊。

## 验收与停止

在项目已有报告中记录下表；状态用 `pass / fail / not_run / not_applicable`，附证据位置与未解决项。硬性正确性问题不能用平均分抵消，未运行不等于通过。

| 检查 | 需要的证据 |
|---|---|
| 目标与契约对应 | 成功条件、检查映射、合法变化和重要假设 |
| 可解性 | 同信息参考路径的运行，或明确标出的未执行论证 |
| 评分双向正确 | 合法替代解通过，错误/边界/作弊样例得到预期处理 |
| 环境与稳定性 | 重建记录、重复运行次数、故障和超时分类 |
| 难度解释 | 实际轨迹与目标难点的对应；没有试跑则不判断难度 |
| 比较有效性 | 适用的版本、预算、重复、分组、分母和聚合记录 |
| 专家复核 | 实际审阅者与意见；缺失明确标记，不以 AI 自评代替 |

只有设计需求时交付任务契约、样例、验证/试跑计划和待决策项，不虚构运行。用户要求实现时交付实际数据/环境、参考解、评分器及其检查、运行与审阅记录；复用项目目录和工具，不默认搭建平台。外部发布仍按用户授权执行。

达到当前请求的验收范围即停止；预算耗尽、必需材料缺失或核心假设被否定时，保留成果并说明当前可支持的判断。禁止持续调题或调分，直到某个模型得到预期名次。
