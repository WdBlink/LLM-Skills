# Good Benchmarks

把用户需要判断的能力变成有证据的评测。以 Ivan Bercovich 的 [Good Benchmarks, v1](https://arxiv.org/html/2607.12217v1) 为基础，结合补充来源作本地适配，不宣称存在适合所有任务的“最佳 benchmark”。来源位置和适配边界见 [source-notes.md](references/source-notes.md)。

## 原则与加载

原文核心：任务来自真实工作；目标充分明确；可在约定资源内解决；验证器接受正确结果并拒绝错误结果；难点属于目标能力；环境稳定；专家审阅实际解题过程。低通过率本身不能证明 benchmark 有价值。

下述执行流程、契约、测试矩阵与跨领域例子为本地工程化设计。新建或重设计时，先按 [检索与复用](references/reuse-existing.md) 调查候选并作需求对照，再结合 [场景选型](references/benchmark-forms.md)、[任务契约](references/task-contract.md) 和 [可执行交付](references/executable-package.md) 确定方案；构建前确定 [结果验收](references/result-acceptance.md) 合同，交付前实际运行验收并处理失败。按问题选读 [案例](references/examples.md)。纯审计沿给定评测的数据与评分调用链核查，必要时定向比较替代方案，不另造平行框架。

**先调查现有 benchmark，再决定补什么。** 默认从用户需求出发开展网络检索，获取最相关候选的实际任务、数据或构建入口、评分代码和运行协议，逐项核验能否满足需求。给出原样复用、适配、组合或新建的有据结论；保留可用组件，只为确认的缺口增加任务、数据或裁判。论文介绍、下载成功或一次工程烟测，均不足以证明候选满足全部评测需求。用户限制联网或仅要求运行指定评测时，遵守范围并记录未核实项。

**先分开选择任务形态和成功依据。** 任务可表现为静态题目、可执行任务包、交互环境、按规则生成的任务、冻结运行记录或现场任务；成功依据可为标准答案、行为测试、目标状态、参考动作、统计判据或 rubric，按目标组合。Agent 自由规划、多轮执行或没有唯一解法，不意味着必须用模型裁判；同一 benchmark 的不同子任务也可使用不同验收器。具体选择、数据边界与适用验证见场景选型，不把某一个科研评审器的形态推广到所有 Agent 任务。

**设计默认包含可复用的裁判产物。** 条件具备时，同步准备测评数据、已保存的评分/运行入口、预期结果和检查证据，不停在“以后编写脚本”的文字计划。复测调用现有入口，不由 LLM 每次重新解释公式或生成评分代码。明确只需讨论时尊重范围；材料不足时完成可做的部分并记录具体缺口，不伪造真实数据或通过状态。

**构建完成由结果验收决定。** 必须取得实际数据集、针对它可运行的入口、可复算得分和现有方法的区分实测；至少两个相关现有方法的真实结果不能由裁判正反例替代。未通过就定位到责任步骤补建、修复与重验，不能用总结或待办清单结束已授权且可继续的工作。程序检查与领域/专家有效性审阅分别保存，二者不能互相代替。

## 执行流程

1. **明确评测需求。** 读取项目规则与已有评测，确认使用者、真实场景、目标能力、比较对象、用途和硬约束。区分固定集合描述与目标总体推断，明确覆盖范围及是否需要区分系统。先确定要观察的行为和评价单位，形成可检索、可逐项核验的需求画像。用一句话说明结果支持的决策和不覆盖的能力，不提前锁定自建方案。
2. **深度检索并判定复用。** 按 [检索与复用](references/reuse-existing.md) 检查项目已有材料，再检索官方论文、仓库、数据和相关版本。获取主要候选并沿任务、数据、评分和运行入口核验，条件允许时做最小复跑。将需求逐项判为满足、部分满足、不满足或未核实，给出证据、缺口和最小补法。优先原样复用，其次适配或组合；只有现有方案不能满足要求或适配代价不合适时，说明依据并新建必要部分。保留来源版本和改动后的比较边界。
3. **建立任务契约与数据边界。** 根据复用决策确定任务形态和成功依据，记录任务说明、可恢复初态、工具权限与预算、输出语义、合法变化和成功条件，给要求分配 ID 并映射到检查。预先确定最终四项验收的评价集/实例要求、指标、现有方法、主要比较和有实际意义的区分标准，不在看到结果后降低门槛。保留外推所需依据，纯结果目标不强加参考路径，多轮过程目标明确真实关系和证据。登记来源、样本/切分、语义参数、seed 和版本，分清被测任务、裁判正反例、裁判校准集和工程测试。求解侧与评分侧隔离，公开可下载不等于允许作为解题输入，隐藏测试不意味着隐藏成功标准。
4. **逐指标确定评分依据。** 对每个指标建立“评价单位—输入样本与版本—判定依据及来源—代码入口/参数—独立预期—输出字段—分母与聚合—执行证据”的对应，优先调用选定方案的现有实现，允许多个指标复用一个模块。能直接验证的采用答案匹配、功能测试或状态检查；动作标注只支持所声明的步骤能力。随机目标预先定义统计判据；主观目标保留 rubric、锚点和人工校准。追踪公式中的模型标签，分开报告客观底线与质量判断。
5. **先跑最小实例并核对可解性。** 保存输入/初态、参考材料、领域评分器和从任意工作目录可执行的命令、依赖与配置。执行任务在实际权限、输入和预算内跑参考路径；仅评审既有记录时，先跑证据包构建和判分流程，将独立参考判断与原任务执行状态分开。参考作者可以知道答案，解题过程却须从提供的信息重建结果；答案评分侧与求解侧隔离。保存产物、日志和资源；合成检查不替代真实输入，未跑的真实任务为 `not_run`，只有可解论证为 `solvability_argued`，研究假设真伪另行验证。
6. **独立检验评分器。** 保存正例、合法替代、边界和错误变体及独立预期；按 [验证矩阵](references/task-contract.md#验证矩阵) 既测误收也测误拒。按评分方式补查规范化是否改变语义、功能与回归测试是否覆盖契约、目标状态及保留条件、参考动作的合法替代、统计误差或评审偏差。必须包含结构合法但核心计算/行为错误的产物，不能只测缺字段；由评分方独立重算能核验的关系。工程测试、合成 fixture 和真人校准分别记录，修共享 harness 后回归受影响任务。已有 benchmark 的名气或历史验证不能替代对所用版本及改动的检查。
7. **冻结集合与比较协议。** 按任务契约说明选样与现有方法参照的理由，固定主要比较、权重、分组和开发/评价隔离；清单或生成/抽样协议均可，保存实际实例与初态。开放研究比较相同起始场景和预算下的运行，不要求系统生成相同提案；任意两份冻结记录不自动构成公平比较。提前确定分母、重试、基础设施故障处理及配对/独立单位/随机来源对应的差异与不确定性分析，不挑最好一次。共享模板、祖先、贡献家族等依赖不能伪装成独立样本。冻结上游版本、适配改动、契约、配置、数据、环境、评分器和参考路径；优先用项目已有检查，否则可用 `scripts/verify_artifacts.py`，但哈希通过不是最终验收。
8. **运行现有方法并解释失败。** 按冻结协议取得至少两个相关现有方法在正式评价实例上的真实产物与得分；已有产物须核对实际数据、系统和协议版本，不能只抄论文总分。记录模型、提示、工具/适配器、记忆与预算构成的系统，以及输入、输出、轨迹、评分和成本；底层模型归因见场景选型。分开检查同一产物的判分波动、同一初态下求解的波动和外部环境漂移；模型裁判的缓存回放不证明重新评审稳定。失败归类为能力、题面、环境、评分器或未确定；诊断提示与变更条件下的成绩独立保存。版本或口径变化须分开报告，重跑受影响基线。
9. **结果验收并返工。** 按 [结果验收](references/result-acceptance.md) 实际执行数据集形成、脚本可运行、得分可复算、方法区分实测四项检查。优先调用项目覆盖四项的入口；固定集合的可分解数值指标可调用 `scripts/accept_benchmark.py`，不改写领域评分器。保存逐项状态、版本证据、分数和主要方法对的差异。失败或未运行项返回相应构建/评分/试跑步骤，补齐后重验受影响项；缺外部必需材料时保留 `needs_input`，不能标完成。程序通过后仍核对契约、评分语义和比较有效性。
10. **审阅与交付。** 让能解决该领域问题的人核对题意和有效性，让了解评测的人核对信息边界和评分漏洞；同一人兼具能力即可。交付复用调查、需求对照、改动记录、最终验收报告及可复跑产物，逐项回答数据在哪里、怎样执行、得分多少、能区分什么。AI 可准备证据和审阅候选意见，但不得冒称已有人类专家确认。缺少专家时仍完成可做的构建与试跑，只交付候选及已验证范围，标 `human_review_pending`。既有用户审阅可作为实际记录，无需为每次编辑重复批准。

## 决策边界

- 不跳过候选调查直接默认从零构建，也不为迎合已有 benchmark 删减用户需求。获取失败、未联网或论文没给细节，应记为未核实或获取受限，不写成“没有现有方案”；明确约束范围内继续可做的检查。
- 不以删必要信息、制造格式陷阱、拼接无关小任务或事后压低预算来追求低通过率。若格式、时延、长程协调本来就是工作要求，可评测它们，但须解释其现实依据并单列归因；不得称其测量了另一种能力。
- 不照着参考实现检查库名、源代码字符串或工具轨迹。只有任务明确要求的接口、真实流程义务或防作弊边界才限制过程，并说明理由；其余合法实现按结果验收。
- 不凭“有 ground truth”“有测试脚本”“公式固定”或“题库冻结”中的任何一项宣称评测已经客观有效。分别验证评分可复算、验收有效和比较公平；没有唯一参考答案不等于没有可执行成功条件。
- 不把“加提示后通过”当作普遍公平的证明；它只帮助区分给定方法下的可解性与原任务的能力要求。对争议领域常识核对权威资料；说明必要假设，保留真正需要推理的部分。
- 固定资源、依赖和数据，保存可重建的版本/哈希。必须联网或接真实硬件的任务另行记录时间、服务/设备状态和配对比较条件；能冻结回放的部分先冻结，剩余漂移单独披露。不得把环境失效悄悄算成模型能力失败。
- 从评分输出、答案文件、可写测试、挂载目录、缓存、网络和重置边界检查绕过路径。攻击测试只在获授权的隔离评测环境中进行；修复后同时重放攻击与正常解，防止封堵使合法任务不可解。
- 小改动导致大幅成绩变化、失败集中于相同答案、反复评审不收敛或成本异常，先检查具体证据。这些是诊断信号，不能单凭其中一项宣布模型差、任务无效或存在作弊。

## 验收与停止

在项目已有报告中记录下表；状态用 `pass / fail / not_run / not_applicable`，附证据位置与未解决项。新建或重设计的 A1–A4 是最终必验项，不能用 `not_applicable` 跳过；运行 [结果验收](references/result-acceptance.md) 的既有入口或适用的本技能脚本取得证据。硬性正确性问题不能用平均分抵消，未运行不等于通过。

| 检查 | 需要的证据 |
|---|---|
| 现有方案检索与复用 | 检索范围和一手来源、候选版本与获取记录、逐需求匹配证据、缺口及最小补法、复用决策和原版/适配版比较边界；受限或未复跑项明确标记 |
| 形态与成功依据 | 评价单位、承载方式、答案/测试/状态/动作/统计/rubric 的选用理由及结论边界 |
| 目标与契约对应 | 目标能力、任务选择、成功条件与检查的对应；合法变化、结论边界及外推假设 |
| A1 数据集已形成 | 实际实例清单、输入/初态/附件、性质/角色、数量/切分与版本；生成/现场任务保留本轮实例，裁判 fixture 不能充当正式评价集 |
| A2 入口可运行 | 针对该数据和方法产物的实际准备/运行/评分命令、依赖、返回码及日志，不只检查文件存在或语法 |
| A3 得分可复算 | 全量逐单位/逐指标结果、原始判定依据、失败分母、权威聚合重算与得分表；独立预期和版本绑定 |
| A4 区分有实测 | 至少两个相关现有方法、主要配对分差和胜/平/负、适用的不确定性/地板/天花板分析；对照事先确定的用途和区分标准，未达标有返工记录 |
| 可解性与评审可执行性 | 任务的同信息参考运行或未执行论证；仅评审时另报证据包/判分执行，原任务执行与科学真伪不随之升级 |
| 评分双向正确 | 合法替代解通过，错误/边界/作弊样例得到预期处理 |
| 环境与稳定性 | 初态重置、判分/求解/外部漂移的分别检查、重复次数、故障和超时分类 |
| 难度解释 | 实际轨迹与覆盖/区分用途的对应；没有试跑则不判断难度 |
| 比较有效性 | 参照理由，版本、预算、独立单位、配对/重复、分组、分母、权重与推断范围 |
| 专家复核 | 实际审阅者与意见；缺失明确标记，不以 AI 自评代替 |

新建或重设计时，在当前授权与可用材料内交付最小可执行包，复用项目目录和工具，不默认搭建平台。若明确只做文字讨论，或缺必要数据、权限、资源，则说明已完成部分、未运行项目及补齐方法；不能把其中一个缺口扩大为全部停留在计划。主观评价保存 rubric、锚点和审阅流程，不强造客观分数。文件齐全、哈希一致、合成样例通过、真实任务可解和独立有效性证据分别报告，不合并成一个“已验证”。外部发布仍按用户授权执行。

构建请求只有四项实测及相应有效性审阅满足约定范围后才能标 `done`。可在当前授权内修复的失败进入 `needs_work` 并继续补建、修复和重验，不以列出缺口代替执行。预算耗尽、外部必需材料缺失或核心假设被否定时保留成果，明确未完成状态、当前可支持的判断及最小补齐动作；只做讨论或审计则按原请求交付，不冒称完成构建。禁止持续调题或调分，直到某个模型得到预期名次。
