# Good Benchmarks

把用户真正需要区分的能力变成有证据的评测。依据 Ivan Bercovich 的 [Good Benchmarks, v1](https://arxiv.org/html/2607.12217v1)；这是 Terminal-Bench 实践方法的本地实现，不宣称存在适合所有任务的“最佳 benchmark”。来源位置和适配边界见 [source-notes.md](references/source-notes.md)。

## 原则与加载

原文核心：任务来自真实工作；目标充分明确；可在约定资源内解决；验证器接受正确结果并拒绝错误结果；难点属于目标能力；环境稳定；专家审阅实际解题过程。低通过率本身不能证明 benchmark 有价值。

下述执行流程、契约、测试矩阵与跨领域例子为本地工程化设计。新建或重设计时，先读 [场景选型](references/benchmark-forms.md)，再读 [任务契约](references/task-contract.md) 和 [可执行交付](references/executable-package.md)；按问题选读 [案例](references/examples.md)，同时看反例。纯审计沿现有数据与评分调用链核查，仅按需加载对应形态，不另造平行框架。

**先分开选择任务形态和成功依据。** 任务可表现为静态题目、可执行任务包、交互环境、按规则生成的任务、冻结运行记录或现场任务；成功依据可为标准答案、行为测试、目标状态、参考动作、统计判据或 rubric，按目标组合。Agent 自由规划、多轮执行或没有唯一解法，不意味着必须用模型裁判；同一 benchmark 的不同子任务也可使用不同验收器。具体选择、数据边界与适用验证见场景选型，不把某一个科研评审器的形态推广到所有 Agent 任务。

**设计默认包含可复用的裁判产物。** 条件具备时，同步准备测评数据、已保存的评分/运行入口、预期结果和检查证据，不停在“以后编写脚本”的文字计划。复测调用现有入口，不由 LLM 每次重新解释公式或生成评分代码。明确只需讨论时尊重范围；材料不足时完成可做的部分并记录具体缺口，不伪造真实数据或通过状态。

## 执行流程

1. **确定判断并选择形态。** 读取当前项目规则与已有评测；确认使用者、真实场景、目标能力、比较对象和用途。先确定评价单位是答案、产物、状态、动作、完整运行还是独立贡献，再按场景选型选择承载方式与成功依据。用一句话说明“这个结果能支持什么决策”，另记不覆盖的能力。纯结果目标不强加参考路径，多轮过程目标则明确需要的真实关系和证据。
2. **建立任务契约与数据边界。** 记录任务说明、可恢复初态、工具权限与预算、输出语义、合法变化和成功条件，给要求分配 ID 并映射到检查及证据。登记来源、样本/切分、语义参数、seed 和版本；分清被测任务、裁判正反例、裁判校准集和工程测试。区分求解侧输入与评分侧答案、隐藏测试和诊断材料；文件公开可下载不等于允许作为解题输入，隐藏测试也不意味着隐藏成功标准。
3. **逐指标确定评分依据。** 对每个指标建立“评价单位—输入样本与版本—判定依据及来源—代码入口/参数—独立预期—输出字段—分母与聚合—执行证据”的对应，允许多个指标复用一个模块。能直接验证的采用答案匹配、功能测试或状态检查；动作标注只支持所声明的步骤能力。随机目标预先定义统计判据；主观目标保留 rubric、锚点和人工校准。追踪公式中的原始标签是否由模型给出，分开报告客观底线与质量判断，不把固定公式称为全程客观。
4. **先跑最小实例并核对可解性。** 保存输入/初态、参考材料、领域评分器和从任意工作目录可执行的命令、依赖与配置。执行任务在实际权限、输入和预算内跑参考路径；仅评审既有记录时，先跑证据包构建和判分流程，将独立参考判断与原任务执行状态分开。参考作者可以知道答案，解题过程却须从提供的信息重建结果；答案评分侧与求解侧隔离。保存产物、日志和资源；合成检查不替代真实输入，未跑的真实任务为 `not_run`，只有可解论证为 `solvability_argued`，研究假设真伪另行验证。
5. **独立检验评分器。** 保存正例、合法替代、边界和错误变体及独立预期；按 [验证矩阵](references/task-contract.md#验证矩阵) 既测误收也测误拒。按评分方式补查规范化是否改变语义、功能与回归测试是否覆盖契约、目标状态及保留条件、参考动作的合法替代、统计误差或评审偏差。必须包含结构合法但核心计算/行为错误的产物，不能只测缺字段；由评分方独立重算能核验的关系。工程测试、合成 fixture 和真人校准分别记录，修共享 harness 后回归受影响任务。
6. **试跑并解释失败。** 冻结契约、配置、样本或生成器、环境、评分器和参考路径的版本/哈希；优先用项目已有检查，否则可用 `scripts/verify_artifacts.py`，见可执行交付。记录被测系统整体配置、预算、输入、输出、轨迹、评分和成本。分开检查同一产物的判分波动、同一初态下求解的波动和外部环境漂移；模型裁判的缓存回放不证明重新评审稳定。失败归类为能力、题面、环境、评分器或未确定；诊断提示与变更条件下的成绩独立保存。
7. **形成集合与比较协议。** 记录覆盖、来源、抽样单位、去重、开发/评价隔离和聚合；固定清单或固定生成/抽样协议均可，保存实际抽样与初态。开放研究比较相同起始场景和预算下的运行，不要求系统生成相同提案；任意两份冻结记录不自动构成公平比较。提前确定分母、重试与基础设施故障处理；报告分组及重复不确定性，不挑最好一次。共享模板、祖先、贡献家族等依赖不能伪装成独立样本。版本或口径改变后分开报告，必要时重跑基线。
8. **审阅与交付。** 让能解决该领域问题的人核对题意和有效性，让了解评测的人核对信息边界和评分漏洞；同一人兼具能力即可。AI 可准备证据和审阅候选意见，但不得冒称已有人类专家确认。缺少专家时仍完成可做的构建与试跑，交付已验证范围并标 `human_review_pending`。既有用户审阅可作为实际记录，无需为每次编辑重复批准。

## 决策边界

- 不以删必要信息、制造格式陷阱、拼接无关小任务或事后压低预算来追求低通过率。若格式、时延、长程协调本来就是工作要求，可评测它们，但须解释其现实依据并单列归因；不得称其测量了另一种能力。
- 不照着参考实现检查库名、源代码字符串或工具轨迹。只有任务明确要求的接口、真实流程义务或防作弊边界才限制过程，并说明理由；其余合法实现按结果验收。
- 不凭“有 ground truth”“有测试脚本”“公式固定”或“题库冻结”中的任何一项宣称评测已经客观有效。分别验证评分可复算、验收有效和比较公平；没有唯一参考答案不等于没有可执行成功条件。
- 不把“加提示后通过”当作普遍公平的证明；它只帮助区分给定方法下的可解性与原任务的能力要求。对争议领域常识核对权威资料；说明必要假设，保留真正需要推理的部分。
- 固定资源、依赖和数据，保存可重建的版本/哈希。必须联网或接真实硬件的任务另行记录时间、服务/设备状态和配对比较条件；能冻结回放的部分先冻结，剩余漂移单独披露。不得把环境失效悄悄算成模型能力失败。
- 从评分输出、答案文件、可写测试、挂载目录、缓存、网络和重置边界检查绕过路径。攻击测试只在获授权的隔离评测环境中进行；修复后同时重放攻击与正常解，防止封堵使合法任务不可解。
- 小改动导致大幅成绩变化、失败集中于相同答案、反复评审不收敛或成本异常，先检查具体证据。这些是诊断信号，不能单凭其中一项宣布模型差、任务无效或存在作弊。

## 验收与停止

在项目已有报告中记录下表；状态用 `pass / fail / not_run / not_applicable`，附证据位置与未解决项。硬性正确性问题不能用平均分抵消，未运行不等于通过。

| 检查 | 需要的证据 |
|---|---|
| 形态与成功依据 | 评价单位、承载方式、答案/测试/状态/动作/统计/rubric 的选用理由及结论边界 |
| 目标与契约对应 | 成功条件、检查映射、合法变化和重要假设 |
| 可复用产物 | 逐指标的数据与评分入口映射、数据性质/角色、配置、独立预期、版本绑定和实际复跑；缺项逐项说明 |
| 可解性与评审可执行性 | 任务的同信息参考运行或未执行论证；仅评审时另报证据包/判分执行，原任务执行与科学真伪不随之升级 |
| 评分双向正确 | 合法替代解通过，错误/边界/作弊样例得到预期处理 |
| 环境与稳定性 | 初态重置、判分/求解/外部漂移的分别检查、重复次数、故障和超时分类 |
| 难度解释 | 实际轨迹与目标难点的对应；没有试跑则不判断难度 |
| 比较有效性 | 适用的版本、预算、重复、分组、分母和聚合记录 |
| 专家复核 | 实际审阅者与意见；缺失明确标记，不以 AI 自评代替 |

新建或重设计时，在当前授权与可用材料内交付最小可执行包，复用项目目录和工具，不默认搭建平台。若明确只做文字讨论，或缺必要数据、权限、资源，则说明已完成部分、未运行项目及补齐方法；不能把其中一个缺口扩大为全部停留在计划。主观评价保存 rubric、锚点和审阅流程，不强造客观分数。文件齐全、哈希一致、合成样例通过、真实任务可解和独立有效性证据分别报告，不合并成一个“已验证”。外部发布仍按用户授权执行。

达到当前请求的验收范围即停止；预算耗尽、必需材料缺失或核心假设被否定时，保留成果并说明当前可支持的判断。禁止持续调题或调分，直到某个模型得到预期名次。
