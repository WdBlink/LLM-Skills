# 解释方法：语言、图解与定制 HTML

先执行下列15条规则，再按实际理解障碍读取后续方法。方法是对原帖方向的工程展开，不是原作者公布的固定步骤。

## 必须执行的15条规则

规则同样用于正文、图中标签、HTML 提示和证据卡。先按规则起草，再逐段检查；具体触发条件、改写对照和检查顺序见后续语言改写规则。

1. **写出执行者与动作。** 把“进行了参数调整”写成“训练脚本把学习率从 A 改为 B”。材料没有执行者或数值时写未知，不补造。
2. **一个概念固定一个名称，一个词固定含义。** 第一次写“评价器（计算模型得分的程序）”，后文持续用“评价器”；另一个对象才使用另一个名称。缩写首次出现给出全称或解释。英文同一词按固定含义和词性使用，如 `close` 表示关闭时作动词，表示靠近时改用 `near`。
3. **消除指代歧义。** “它”“这”“该方案”可能指向两个对象时，替换为对象名，例如“缓存失效后，服务重新读取数据库”。
4. **拆开多个判断。** 一句同时包含做法、结果和建议时，分别写。若出现两次转折、嵌套条件或三个连续动作，检查是否需要拆句；不为缩短句子切断条件与结论的关系。
5. **把条件写在对应结果旁。** 用“在 X 条件下，Y 从 A 变为 B”；保留“只有”“至少”“最多”“可能”等限定。条件只属于一项结果时，不扩大到整段。
6. **操作每步只要求一个可完成动作。** 写“打开配置文件”“把 timeout 改为 30 s”“重新运行请求”。存在依赖时按先后顺序列；确需同时操作时明确“同时”。
7. **将空泛评价替换为可检查的内容。** “表现较优”需改成指标、对照与范围；“优化资源配置”需说明调整了什么。来源没有这些信息时写“材料未说明”，不生成具体数字。
8. **解释机制时展示中间一步。** 用给定或明确标为演示的具体输入，写出输入、规则、产生的中间状态和结果。因果机制尚未验证时标为假设，不能用“因此”把相关结果连成因果。
9. **数字带单位和比较对象。** 明确基线、指标方向、分母/样本范围；区分比例、百分比与百分点。相对变化给出计算依据，不能把两个不同条件下的值直接相减后称为提升。
10. **一段回答一个问题，描述段默认最多 6 句。** 首句回答该段的问题，其余句子补机制、例子或证据；超过 6 句或话题转到另一对象/结论时分段。定义、公式或原文引用需要完整展示时独立列出。多个并列选项用表格或列表比较。
11. **写明否定与不确定性的对象。** “尚未测试高并发”不能改成“高并发失败”；“可能降低延迟”不能改成“会降低延迟”。指令直接写动作或禁令，避免双重否定。
12. **限制英文长句和名词串。** 默认将操作句写到不超过 20 词、描述句不超过 25 词，连续名词不超过 3 个；超过时拆句或用介词/动词展开关系。完整定义、必要限定、代码标识或原文引用无法拆开时保留并单独展示。中文按判断和动作拆句，不套英文词数。
13. **英文用明确的动词形式。** 指令用祈使句；描述优先一般现在、过去和将来时，允许不定式及作形容词的过去分词。将可无损改写的进行时、完成时改成简单时态；操作中的被动句改成主动指令。`-ing` 属于技术名称或时态差异会改变原意时保留；不要为形式改变事件先后或持续状态。
14. **不要为省字删除关系词。** 英文保留必要的 `the`、`a`、`this`，具体指代仍须明确。中文保留“在、之前、之后、至少、只有”等决定对象关系与范围的词。先减少空泛词，再拆句，不删这些词来满足长度限制。
15. **安全说明先写动作，再写后果。** 确有伤害/损坏风险时，先写“不要做什么/满足什么条件后再做”，下一句说明具体风险。技术说明中 `WARNING` 表示人身伤害风险，`CAUTION` 表示设备损坏风险；普通证据不足使用“未验证”，不套安全警告标签。

原帖中的语言规范名称只用于记录来源。执行技能时按上述规则操作，不把“接近某标准”当作写作指令或完成判据。

## 语言改写规则

执行时不需要掌握某个受控语言标准。以下规则是本技能的操作合同；来源归属单独记录。这些规则适用于中文和英文，词数检查点仅适用于英文。

### 遇到什么，具体怎么改

下表均为虚构示例。只使用输入已提供的信息；缺失时保留未知。

| 检查对象/触发情况 | 必须执行的改写 | 前 → 后 |
|---|---|---|
| 被动句隐藏执行者，材料已给出执行者 | 补具体主体，用动词说明动作 | “结果被评价器保存” → “评价器保存结果” |
| “进行、实施、实现”后跟抽象动作名词 | 改为直接动词；普通词能表达同义时用普通词 | “进行参数的初始化操作” → “初始化参数”；英文 “utilize” → “use” |
| 多个词指同一个对象 | 选一个规范名称，全文统一；确有不同对象时解释差别 | 同一程序交替称“评价器/打分引擎/评估模块” → 全文用“评价器” |
| 首次出现缩写或陌生术语 | 先给读者所需的含义，再使用简称 | “使用二分查找” → “二分查找每次排除一半候选位置。它要求数据已排序” |
| 代词有两个可能的先行对象 | 直接重复实际对象名 | 已知失败的是缓存：“服务访问缓存，但它失效了” → “缓存失效后，服务重新读取数据库” |
| 同句塞入做法、结果、建议 | 按三个判断拆开，分别保留证据/限定 | “启用缓存后延迟下降但只测一次所以应再测” → “启用缓存后，本次延迟下降。只测试了一次。建议重复测试” |
| 条件离结果远、范围不明确 | 将条件放在对应判断附近，保留必要/充分条件的原意 | “性能有所改善” → 有源数据时：“在并发为 1 时，p95 延迟从 100 ms 降至 90 ms” |
| 一个操作步骤包含多个依赖动作 | 拆成按顺序可执行的步骤 | “改 timeout 后运行请求并查看日志” → “1. 把 timeout 改为 30 s。2. 运行请求。3. 查看日志” |
| “更好、显著、较优、有效”等无标准评价 | 找到指标、基线、范围；未给出就指出缺失 | 仅有“性能更好” → “材料称性能更好，但未提供指标、基线或测试条件，暂不能判断改善幅度” |
| 有结论、没有中间关系 | 用一个具体输入走一次规则，展示中间结果 | “二分查找很快” → “在 8 个已排序候选位置中，每次比较后最多保留 4、2、1 个位置” |
| 数值缺单位、分母或对照 | 按来源补齐；区分差值和相对变化 | 已知准确率：“从 80% 升至 84%，提高 4 个百分点；相对提高 5%，即 (84−80)/80” |
| 推断写成事实、未知写成失败 | 恢复证据强度及否定范围 | “单次提升证明稳定改善” → “本次结果改善；稳定性尚未验证” |
| 一段跨多个对象或问题，或描述段超过 6 句 | 按问题分段；并列项使用可比较的列表/表格，定义/引用独立展示 | 同段混写方法原理、测试结果和预算 → 三段分别回答“怎么工作、测到什么、要花多少资源” |
| 英文句子/名词串超长 | 默认操作句最多 20 词、描述句最多 25 词；连续名词最多 3 个，超过时用介词/动词展开或拆句 | “model output quality evaluation procedure” → “procedure for evaluating the quality of model outputs” |

长度要求用于处理可拆开的普通说明。完整定义、必要限定、公式、代码标识和原文引用无法拆开时单独展示，不删去信息来满足长度。主动语态的执行者未知时，保留被动表达或写未知；不能为了让句子看起来直接而编造主体。中文不强行逐词翻译英文规范。

### 英文动词、词义和安全说明

下列形式来自用户提供的概览图，表中的新例句是本技能示例。使用默认形式；若改写会改变语义，保留准确形式。

| 句子用途/形式 | 具体规则 | 示例 |
|---|---|---|
| 操作指令 | 祈使句，直接写动作 | `Close the valve.` |
| 一般现在时 | 描述规则或当前事实 | `The valve closes when the pressure rises.` |
| 一般过去时 | 描述已经发生的事件 | `The valve closed at 10:00.` |
| 一般将来时 | 描述未来事件，保留其确定程度 | `The script will save the result after the test.` |
| 不定式 | 表达目的，不堆叠抽象名词 | `Turn the knob to open the valve.` |
| 过去分词作形容词 | 表达对象状态 | `Inspect the closed valve.` |
| 进行时 | 可无损替换时改简单时态；正在持续的动作与技术名称按需要保留 | 当前开关状态：`The switch is controlling the pump.` → `The switch controls the pump.`；需要强调持续过程的“正在关闭”不改成“已关闭” |
| 完成时 | 能用一般过去时和时间关系准确表达时改写 | `The script has saved the result.` → `The script saved the result.`；影响事件先后的 `before/after` 必须保留 |
| 操作中的被动句 | 改为主动指令；执行者是操作者 | `The valve must be closed.` → `Close the valve.` |
| 描述中的被动句 | 已知执行者时补主体；未知或执行者无关时可以保留 | 已知是评价器：`The score was calculated.` → `The evaluator calculated the score.` |

用词要同时固定含义与词性。例如 `close` 表示“关闭”时作动词；不要同段又用其形容词含义表示“靠近”，改用 `near`。技术名称和技术动词可保留，首次解释其含义；不将代码/API 名称改成同义词。

附图给出的普通词替换可直接用于英文改写，但先检查所在句是否仍表达同一意思：

| 原表达 | 使用 |
|---|---|
| `commence` | `start` |
| `ensure` | `make sure` |
| `prior to` | `before` |
| `replenish` | `fill` |
| `utilize` | `use` |
| `approximately` | `about` |
| `in order to` | `to` |

保留必要的冠词和指示词：`Close the valve.` 不压成 `Close valve.`；`this valve` 仍需能辨认出是哪一个。中文同样保留范围和时序词，如“仅在测试完成后保存”，不能压成“测试保存”。

安全说明只用于实际风险，分成明确动作和具体后果两句。例如：`WARNING: Do not touch the hot surface. It can burn your skin.` 先给禁令，再说明伤害。设备损坏使用 `CAUTION`。不能把“不确定”“证据缺失”等普通分析边界包装成安全警告。

### 起草和复核的顺序

1. 从材料提取要解释的对象、动作/关系、条件、数值、否定和未知项。只有一段总结时，先检查其是否包含支持解释所需的信息。
2. 为容易混淆的对象选定名称；首次出现时解释读者需要的术语。短解释可在脑中完成，不要求创建术语文件。
3. 每段先回答一个读者问题，再展示必要的一步机制、例子或证据。操作按依赖顺序列步。
4. 对照原始材料逐句检查：主体是否补造，条件归属是否改变，“只有/可能/尚未”等限定是否丢失，数字/单位/比较对象是否一致，相关是否误写为因果。
5. 按表中触发条件重读：固定对象名称，替换有歧义的代词，拆开多个判断，删除空泛评价；英文检查时态、冠词、句长和名词串，描述段检查主题和句数；改写后再次核对事实。没有触发问题时不强行重写。

### 完整改写示例

输入材料（虚构）：同一硬件、并发 1、同一批 100 个请求；只运行一次；p95 延迟从 100 ms 降至 90 ms；正确率和其他负载未测。

待改写：

> 经综合评估，本方案在资源约束条件下展现了较优的性能表现，为进一步优化奠定了基础。

输出：

> 在相同硬件、并发为 1 的这批 100 个请求上，p95 延迟从 100 ms 降到 90 ms，下降 10%。p95 表示约 95% 的请求延迟不超过这个值。本轮只运行一次，稳定性尚未验证。正确率和其他负载未测试。

数值来自输入材料；10% 来自 `(100−90)/100`。若输入只有待改写句而无测试数据，应输出“材料未提供指标、基线和测试条件，暂不能判断性能是否改善”，不能借用示例补出数据。

语言检查通过的判据：对象能识别、动作/关系能复述、条件与比较范围可见、没有歧义指代、数字及不确定性与来源一致。无需向用户展示内部检查清单，也不能声称符合完整受控语言标准。

## 图解让读者直接看见关系

先写清图要回答的问题，选最相关的一种关系：结构、过程、依赖、空间、数量变化或方案差异。

- 从读者熟悉的对象开始，展示关键中间环节，标记输入和输出。
- 连线有明确含义，例如“调用”“依赖”“测量”“假设导致”，而非一律画箭头。
- 数据图的轴、单位、分母和范围可见；结构图的布局与距离不要冒充数值尺度。
- 已证实边、假设边和未知项用文字/线型区分。图不能凭直觉增添因果。
- 用一个具体案例沿图走一遍，再说明一般关系。图旁文字解释读图方式和限制，而非重复全部标签。

图的验收：读者能沿着关系找到“输入如何成为输出”，或指出方案的关键差别。精致的卡片排列本身不构成图解。

## HTML 是围绕问题定制的解释器

使用 HTML 的理由可以是**动态过程和抽象机制**，不必是大量实验。先用一句话定义：读者操作什么，能观察什么，从而理解什么。

| 理解问题 | 读者动作 | 可见反馈 |
|---|---|---|
| 参数变化为什么影响结果 | 拖动一个有范围和单位的滑块 | 图形、数值和一句机制解释同步变化 |
| 算法/系统如何一步步工作 | 点击下一步、暂停/重置 | 当前步骤、变化的对象和中间状态可见 |
| 两种方法为什么不同 | 切换情景或并排比较 | 相同输入下，差异发生在哪一步 |
| 数字是否只在某条件成立 | 切换条件、展开证据 | 当前数据范围、结果和来源一起变化 |

避免做成只有首页、指标卡和下载按钮的报告壳。采用最少足够的交互：滑块、逐步按钮、情景切换、证据展开。一个控件可以比完整 App 更有效。

例如解释串联系统可靠性，可让读者改变部件数量与单部件可靠性，观察独立假设下 `R = p^n` 的曲线和结果。模型旁始终写明“独立、全部部件工作才算成功”；演示数值标为公式计算，不声称是测量。切换情景应帮助读者理解为什么假设变化会影响结论，而非让读者把理想模型套到所有系统。

### 制作与验证

1. 先建立解释路径：一个熟悉的例子、关键关系、读者可操作的变化、结果与边界。只保留完成理解任务所需内容。
2. 用本地、自包含 HTML/CSS/JS 实现。来源文本转义；数值来自记录或标注的公式模型。动画帮助追踪变化，提供暂停/重置和减弱动态效果；不要只为视觉加自动运动。
3. 控件有标签、单位、范围和当前值，键盘可用。条件变化后，同步更新数值、图形和解释；筛选需显示范围/条目数、空结果和重置。限制保持首层可见。
4. 按实际计算检验模型的已知点/边界点，按来源检验观测数据。打开页面执行读者动作，检查反馈、重置、边界输入及小屏布局。不将仅成功写出 HTML 文件称为交互验证。
5. 交付可直接打开的文件，并用一两句话说明先操作哪个控件、要观察什么。产物可以在本次理解任务结束后弃用，无需自动追加账户、后台、持久化或发布流程。

## 可理解性的最低检验

生成后在内部检查一个迁移问题：当条件改变时，解释是否足以让读者预测变化？例如“同一 p 下增加串联部件，系统可靠性如何变化，为什么？”不强制让用户考试，也不把自己的预测当作用户已经理解的证明。

如果读者仍需在脑中完成多个未展示的中间步骤，补一个例子、图或可操作的模型；如果产物只需读一句话就能明白，缩减无帮助的交互。解释充分时结束，不为丰富载体无限增加功能。
