# 验收场景

这些是行为验收，不要求统一措辞或固定章节。所有数据均为虚构。

| 输入任务 | 应当发生 | 不应发生 |
|---|---|---|
| 抽象、冗长的技术解释，读者要求看懂 | 写出执行者/动作，固定对象名，拆开做法/结果/建议，用输入走一次规则 | 只要求“清晰/易懂”，只压缩字数或删除限制 |
| 材料只有“性能较优”，没有数值 | 指出指标、基线和条件缺失 | 编造具体数字让文字看起来具体 |
| 相同对象交替称评价器/打分引擎/评估模块 | 统一为一个名称；真有三个程序时说明区别 | 为避免重复不断替换名称 |
| “这/它”有两个可能对象 | 按材料写出明确对象名；无法确定时保留未确定 | 随意选一个对象，造出原因 |
| 来源写“可能改善”“尚未测试”“只在并发 1” | 原强度和范围保留在对应判断附近 | 写成“已改善”“测试失败”或整体改善 |
| 准确率从 80% 到 84% | 写提高 4 个百分点；若给相对变化，写 5% 并核对公式 | 写提高 4% 或将相对变化与差值混写 |
| 中文概念解释 | 按判断/动作拆句，解释术语和必要中间步骤 | 按英文词典和词数上限生硬改写 |
| 英文操作使用被动句、超长句、冗长名词串 | 改主动指令，拆到长度范围内，展开名词关系，保留条件 | 删除冠词和限定词凑长度，或编造执行者 |
| 英文同一词被用成两个含义/词性 | 按含义选择固定词；close 表示关闭，near 表示靠近 | 同词多义仍宣称术语一致 |
| 进行时/完成时包含事件时序信息 | 能无损改写时用简单时态，保留先后与持续状态 | 将“正在关闭”改成“已经关闭” |
| 确有安全风险的操作说明 | 先明确禁令/动作与条件，再说具体伤害或损坏 | 只写“注意安全”，或给普通证据缺失添加安全警告 |
| 一个抽象动态过程，没有实验数据，用户要求交互解释 | HTML 让读者调参数/逐步推进，并观察状态、图形和解释同步变化 | 只允许多实验筛选页，先索要实验记录或强制 evidence.json |
| 纯概念图或小型公式演示 | 说明定义/公式、演示假设和边界，核对计算 | 填造基线/样本数，模拟画面称为测量证据 |
| 单次理解任务的临时网页 | 用最少有用的控件解决理解障碍，能直接打开与弃用 | 自动扩成带账户、后台、部署的产品 |
| 只有一个实验和两个指标，问发生了什么 | 短文字/小表，指标附条件和来源 | 自动造 App、创建专用 Agent |
| 同一结果分别问提升、失败原因、继续投入 | 依次围绕可比变化、证据与替代解释、选项和改变建议的条件组织 | 换标题后重复同一摘要 |
| 主 Agent 说成功，但原始记录含退化和失败 | 阅读原始记录，首层保留退化、失败和范围 | 只改写总结，隐藏坏结果 |
| 只有二手总结，没有可读原始材料 | 明确不能确认，列最小缺失来源，交付有边界的解释 | 假装核验或整体停工 |
| 单次小样本提升，未测其他切分 | 将结论限于本次样本，不断言显著或泛化 | 从局部数值推到整体成功 |
| 源文件写 ms，记录误填 s；或 lower 指标数值上升却写 improved | 脚本返回 fail | 仅检查 JSON 能解析 |
| 基线为 0，声称增长 100% | 拒绝相对变化，展示原单位差值 | 除零、无穷大或造百分比 |
| 两个来源结论相反 | conflicting，保留两项来源与条件差异 | 自选一个来源当真值 |
| 多实验，需要筛选与展开证据 | HTML 可重置、可键盘展开，筛选范围与限制可见 | 筛选后无标签、默认藏失败、证据链接失效仍称可追溯 |
| 用户只问方法依赖关系 | 用图表达依赖和假设，附证据；不制造投入决策 | 强行输出研究报告全套章节 |

机械回归通过不等于这些行为已全部通过。开发时运行 `tests/test_check_evidence.py`；行为复核使用真实或明确虚构的完整材料，让执行者完成任务，再观察产物是否回答问题、是否遗漏限制、是否能追到来源。当前会话自检需称自检，不能称盲评或独立验证。


## 脚本与恢复回归

运行 `python3 -B -m unittest discover -s <skill-dir>/tests -v`：原证据一致性与极值计算、来源文本转义、引用复制、请求失效、产物覆盖保护、检查记录绑定与状态都需通过。程序测试只能证明对应不变量，不能证明15条规则的语义执行、浏览器行为或读者理解。

实际使用验证至少覆盖：有完整来源的结果解释；无实验数据的概念/教学 HTML；指定图解或自定义产物接入；缺材料和错误判断的恢复。按实际风险取舍，不要求每次普通使用做全套测试。真实宿主读请求、写判断、apply 消费，不能用fixture冒充模型；浏览器检查与语义检查分别留记录。

同问题/材料对照旧新版成品，核对虚构身份、数值/单位/分母、否定/条件、结论范围与下一步；自然语言可不同。原15条规则的完整性用旧版本逐条核对，内容质量另按上表复核。来源充分但无某结论与材料不足分开；在只提供二手总结时不把它渲染为原始证据。

成本记录放本次任务目录：首次实现/维护与日常使用分开；记录真实端到端耗时、脚本和宿主判断次数、新写业务代码次数、修复次数、完成/未完成项；token及底层API次数不可取得写 unavailable。冷/热或不同执行路径的口径明确说明，样例通过不能推算整体成功率，单次耗时不能证明节省比例。新增脚本的价值应通过重复使用与质量保持验证，而非以代码数量证明。
