# 群晖公网发布

把指定服务发布到用户选定的公网入口，并证明真实外部网络能安全使用它。成功条件不是“配置保存”或“局域网能打开”。

典型链路：`外网 IPv6 客户端 → 域名 AAAA → 群晖 HTTPS:入口端口 → 内网服务 IP:应用端口`。

## 接手与边界

- 先明确或从现场推断：应用位置与端口、NAS、域名、期望入口、客户端是否需要 IPv4。缺应用目标时才问；不把普通端口选择变成问卷。
- 复用已运行服务、已登录管理页面、有效证书和现有 DDNS。读取项目部署规则；本技能不要求迁移到 Docker 或 systemd，也不要求重建应用。
- 如果用户提供了网络记录，用它定位设备和现有规则，再现场核对地址、端口和配置。操作以当前任务的授权为准。
- 保存本次涉及配置的原值与回滚方法。只操作目标服务，不调整 NAS 存储、现有管理入口、其他站点或全网安全策略。
- 发布请求覆盖必要的常规操作；不重复询问已明确授权的事项。若当前工具要求提交时确认，先完成可独立执行的核验和表单准备，再一次列清具体变更、影响与规则来源。创建技能、登录完成不等于确认待提交的公网变更。

## 先确认应用可用

1. 从实际运行主机核验服务、监听地址、版本和常驻机制。user systemd 除 active 外检查 enabled、Linger；容器检查现有重启策略。仅绑定内网地址不等于防止路由器转发暴露。
2. 从 NAS 所在网络访问后端；可以从 NAS 发起时优先直接验证 NAS→后端路径。分清健康检查、首页加载和实际业务调用。
3. 发布前验证必要鉴权：未授权请求不能读受保护数据或执行付费操作；授权后至少跑通一项核心操作。保留应用已有访问控制。若没有适合公网的鉴权，先解决它，不以“隐藏端口”替代。
4. 检查应用对反代的要求：公开 URL、回调地址、可信 Host/代理、Cookie Secure、WebSocket/SSE。只调整确有要求的项，不把所有请求头视为可信。
5. 读取配置时不输出密钥或 Cookie；测试在原主机内读取凭据。不要为验证把 API key 写进 URL、命令参数、报告或浏览器日志。

## 确认公网链路

- 查看浏览器已打开的管理页面和现有配置，不能因为 5000/5001 不通就宣称 DSM 不可管理；它可能用了自定义端口。
- **IPv6**：核对 NAS 的全局 IPv6、域名 AAAA、路由器入站规则与 NAS 防火墙。一般不需要 NAT 端口转发；群晖可以接收 IPv6 后反代到内网 IPv4 服务。
- **IPv4**：查看路由器 WAN 地址并与外部出口地址对比。只看 IP 查询网站返回公网地址不能排除 CGNAT/双重 NAT。IPv4 访问确有需求时才配置目标 TCP 端口转发到 NAS。
- **DDNS**：DNS 指向正确和 DDNS 自动维护是两个独立事实。找出实际更新者（DSM、路由器、容器或脚本）、更新的记录类型、最近状态及绑定的网卡/地址。DSM 列表为空不等于没有其他更新者；找不到时说明自动更新未验证。避免第二个更新者与现有任务互相覆盖。
- **解析**：同时核对 A 与 AAAA。fake-IP 环境用可信 DoH 或合适的直接查询复核；公共递归解析器不是权威 DNS。`--resolve` 只验证指定地址链路，不能证明 DNS 正常。
- **域名加端口**：如 `https://service.example.com:9443`。DDNS 只维护地址，端口属于 URL/监听配置；非默认端口仍必须用 HTTPS。证书匹配域名，不匹配端口。不要让用户改用裸 IPv6 地址从而绕过证书或 Host 校验。
- 不自动把现有共享域名改成 IPv6-only，不删除影响其他服务的 A 记录。若明确只支持 IPv6，说明 IPv4-only 客户端不可用；客户端兼容性要求决定是否另设 AAAA-only 子域名或保留双栈。

## 配置最小入口

1. 优先复用/修改目标服务自己的反代规则；确认来源协议、域名和端口不冲突。443 不可达时，先区分后端、NAS 防火墙、路由器和运营商；不能仅凭超时就断言运营商封禁。用户接受域名加端口时选一个未占用的高端口。
2. DSM 入口通常是“控制面板 → 登录门户 → 高级 → 反向代理服务器”，以当前 UI 为准。来源为 HTTPS 域名:入口端口，目的地为实际后端协议/IP/端口。
3. 核对该规则绑定的证书及有效期、链、续期方式。高端口不会让 HTTP-01 自动改用该端口；复用证书或适用的 DNS-01/现有续期机制，不为申请证书盲目开放其他端口。没有可用证书就标记阻塞，不能用关闭校验冒充成功。
4. 按真实操作耗时设置反代读取/发送超时。SSE 验证数据持续到达；需要时关闭对应代理缓冲，不能靠增加超时替代流式验证。WebSocket 仅在应用需要时配置 Upgrade。
5. 只放行目标端口/必要地址范围，保留防火墙。IPv6 不添加无意义的 IPv4 NAT；IPv4 转发目标是 NAS，不绕过已选定的 NAS 入口。
6. 后端、反代、DNS 可独立准备，没有“必须先改 DNS”这一固定顺序；在可行时先定向测试反代，再切解析。每次保存后读取实际生效值，遇到失败按证据定位，不盲重试或扩展端口范围。

## 验收与交付

按 [verification.md](references/verification.md) 分层验收，记录每次探测的网络位置、IP 版本、地址、端口和结果。

- NAS/后端本地链路、真实 DNS、TLS、浏览器访问控制、授权后的业务操作都要验证。
- **从同一局域网访问公网 IPv4/IPv6，即使 200，也不是外网验收**；NAT 回流和同网段 IPv6 会掩盖入站问题。
- 用受控外部主机或用户关闭 Wi-Fi 的移动网络验证。IPv4 探针不能证明 IPv6 失败或成功；第三方探针失败只是该位置的失败。没有独立 IPv6 出口时，先完成其他检查，再请用户做一次明确的手机测试。
- 以请求的网络覆盖为准：IPv6-only 服务只有 IPv6 验收通过即可，但明确这一限制；双栈需分别验证。页面出现不等于业务成功，至少一项核心操作必须通过完整反代链路。
- 外部访问仍失败时，保留已完成成果，准确列出未完成项和下一项必要输入，不宣布发布成功。出现需改变入口、网络覆盖或工具授权的情况时，只暂停依赖该决定的部分。
- 成功后清理本次创建且已确认不再需要的旧入口/转发，保留回滚信息；遵守当前工具的删除确认要求，不动既有管理规则。
- 更新项目现有部署记录；没有时写一份简短状态文件：最终 URL、后端、反代、DNS/DDNS 更新者、证书/续期、鉴权方式、外网测试证据、回滚与未完成项。无凭据正文。
- 给用户可点击的最终地址和实际验证范围；动态地址自动更新未验证时，不承诺长期无人值守可用。
