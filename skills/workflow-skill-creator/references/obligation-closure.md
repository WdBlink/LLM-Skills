# 批准的要求必须一直约束到交付

一个阶段运行稳定，并不意味着用户要求被后续流程履行。PaperFlow 的失败案例：
用户审阅摘要列出 6 图、2 表，冻结 Brief 只留下概括要求；规划和评审提示词虽然
要求遵循 Brief，最终程序却仅检查通用最低数量。真实稿件的 2 图、3 表因此可能
通过图表子检查，尽管不是原计划内容。可打开的 PDF 也曾被误解为已完成交付。

## 重构前后都检查的链路

`用户要求 → 实际批准对象 → 任务输入/依赖 → 产物与证据 → 消费位置 → 逐项验收 → 完成状态`

- 展示的计划和运行契约必须来自同一结构；不要让模型另写更具体、却未冻结的摘要。
- 每个必交项有稳定 ID、目的、内容/证据要求和验收标准。模型可帮助解释和拆分；
  程序复制 ID、绑定版本、维护覆盖关系。不能用总体数量代替每项内容。
- 按当前证据动态拆分任务，复用共同上游。已有明确参数的机械步骤由默认入口直接派发，
  而不是新增工具后仍等模型选择。给生成任务参数的模型提供实际目标 schema，
  不让它面对无类型 `arguments: object` 猜字段。
- 稳定脚本执行受校验的计划数据，优先扩展已有 WorkOrder/调度器。用户确需导出代码时，
  才用固定模板生成薄入口；脚本语法通过不证明任务覆盖、权限、恢复或科学内容正确。
- 文件存在、worker completed、科学结果为正、要求得到满足、允许最终交付，是不同事实。
  缺失或阻塞要持续可见；负结果可以是有效成果，但不能自动注销原定比较与证据要求。
- 机械校验检查 ID、来源/版本、文件、依赖与实际插入位置；独立模型按项判断语义与证据
  是否相符。不能让生产者自报完成替代独立核验，也不能让总分覆盖某个未满足项。
- 调整研究范围或减弱必交项应修改批准契约；常规任务顺序和方法调整不要新增人为审批。
  不追写历史审批。旧格式无法证明完整覆盖时明确缺口，不能静默套用通用门槛。
- 输入、产物或绑定变化使相关评审失效；未变的独立工作继续复用。未知外部副作用
  沿已有 reconciliation 处理，不为了恢复便利重复付费或重复执行。
- 区分历史数据读取模型与实际发给服务商的提交 schema。为兼容旧记录新增的默认值，
  可能让字段从 `required` 消失，导致严格输出接口拒绝整个请求。检查最终传输的
  schema，包括嵌套对象的必填字段和 `additionalProperties`；不能只测本地解析成功。
  服务错误保留有界私有诊断，失败调用和未知用量也计入验证记录。

## 能反驳假完成的最小检查

对用户要求构造有针对性的缺陷注入，验证最终完成入口会拒绝，而不只验证 helper：

1. 去掉一个必交产物；用无关产物补足总数，仍然不能通过。
2. 产物存在但没有进入最终文稿，或数据/版本变化后复用旧评审，必须拒绝。
3. 数量、文件和类型都正确，但内容不回答要求，独立审阅必须能记录 unmet 并阻止交付。
4. 全部项确实满足的受控正例能通过相应子检查，避免把“一律失败”误当修复。
5. 真实默认入口执行脚本调度，完成任务在恢复时不会因新增 ID 而重跑；
   动态依赖错误、局部失败和 uncertain 效果仍保留原有边界。

测试夹具、真实研究材料回放、真实模型判断、完整科研交付分别记录。故意注入的错误
内容和测试批准不能成为真实研究事实或人类审批。报告全部模型尝试、耗时、token，
费用无法取得时写 unavailable；一次成功不证明通用可靠性，不宣称消除了模型误判。
