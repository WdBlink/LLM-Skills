# 从任务到可执行 Skill

这是任务定义与选型参考。默认采用 [当前宿主判断接口](judgment-interface.md)；只有独立审查或复杂编排需要时，再读 [实现教程](implementation-walkthrough.md)、[宿主派发](host-dispatch.md) 和高级 evidence-brief 示例。不是要求每个生成物都有同一文件树。短任务在 SKILL.md 中回答关键问题；复杂工作才维护独立阶段合同。章节：任务合同、领域判断、阶段边界、工具与数据、路由与失败、验证、写作。

## 编写期与执行期分开

编写期读取实现与调用方，固化重复算法，设计参数与判断合同并验证。日常执行期直接调用现有入口，只加载使用合同和判断材料，不重写同一算法或先读全部源码。

文件名、列名、语言、阈值、模板等差异用参数表达，声明默认值、允许范围和未知值处理。一次性差异可在任务目录加小适配；反复出现或明确要求扩展时才维护核心实现。不先设计插件系统或工作流 DSL。

少量语义判断由当前宿主完成。只有独立审查、批量或无人值守等实际需求才拆子调用。跨文件交接绑定材料快照、目标、规则版本和语义参数；输出路径等非语义参数可以后选。模型给 ID/允许字段增量，程序复制事实。信息不足与无符合项必须区分。

## 1. 从一个真实使用场景开始

先描述“用户交给什么，最后拿走什么，怎样使用”，然后反推实现。不要从“应该有几个 Agent”或“应该选什么框架”开始。

有参考仓库时，沿一次实际入口追到输出：
- 安装/调用入口以及实际依赖；
- 中间数据与消费者，真正的调用关系；
- 失败、重试、终态，以及文档与代码的差异；
- 声称的隔离、校验、版本一致性由什么代码或宿主能力保证。

对关键强保证找一个反例：空输出能否被当作成功？旧检查是否会被新输入复用？工具失败是否被转成空列表？这一步可直接决定后续是否需要额外机制。

任务合同可以只是下面几行。按实际任务填，不创造未知条件：

```text
输入：原始请求、材料、不可改变的限制
输出：文件/答复/操作结果，谁来消费
质量：必要的内容标准、可验证条件、不能证明的部分
副作用：读取与写入范围、已授权外部动作
缺失与失败：关键缺口时的行为、允许的部分交付
```

用户偏好与硬约束分开；模型推断的默认值不得伪装成用户明确指定。实际预算和操作权限不能从其他项目默认移植。

## 2. 建立领域判断依据

Skill 的价值不是把普通步骤写得很长，而是把 Agent 容易缺少的领域标准落到具体决策上。

每条重要规则回答：
- 它解决哪个真实失败或满足哪个验收要求？
- 有什么可靠来源、样例或标准？
- 谁检查：程序、执行实验、模型评审或人？
- 不满足时是阻断、修复还是提醒？
- 在什么输入下不适用？

有案例库时保留正例与失败例；不要只列“优秀风格”。没有数据时标为待验证启发式，不把它称为经验规律。跨领域迁移时重新核对前提，例如研究论文的 novelty 不能直接成为客服答复的目标。

把创作空间与真实性要求分开：可以要求说明假设、引用来源、比较朴素方案，不必强制每次输出多个方案或套同一创新框架。遇到理论题、无图片材料等形状，允许诚实的不适用，不填假内容凑字段。

## 3. 用阶段合同决定拆分

阶段值得独立，通常因为它：
- 有可独立消费、验证或重跑的输出；
- 需要不同工具、成本或证据；
- 与前阶段存在自评偏差；
- 拥有不同的修改权或副作用。

一个最小阶段表即可：

| stage | inputs | outputs | executor | acceptance | failure/retry |
| --- | --- | --- | --- | --- | --- |
| 实际阶段名 | 具体文件/字段及来源 | 消费者需要的内容 | 程序/模型/宿主/人 | 可检查条件及执行者 | 修复位置、停止条件 |

不要把流程中的每个动词都做成一个阶段。选择与生成可以共享上下文；创作与挑错在偏差明显时分开。隔离可以通过新模型调用、宿主子 Agent 或上下文重置实现；并非每个宿主都有同一工具，缺少能力时诚实说明降级。

只向审查者传完成判断所需的内容，不能为“盲审”隐藏阻断证据或用户硬约束。成功路由应以有效输出为依据，模型可给结构化领域 verdict，由程序或明确合同限制合法后继；“程序路由”不等于领域决定全由代码完成。

## 4. 把确定性工作交给现成程序

先查实际代码、CLI help、已有脚本和已安装技能。优先：
1. 同项目已存在的实现；
2. 标准库或平台原生能力；
3. 已安装并验证接口的依赖；
4. 仅为缺口增加最小代码。

适合程序：解析、去重、关联、路径转换、字段类型、守恒/一致性检查、允许字段 merge、布局测量、文件生成。
适合模型：理解意图、解释来源、提出方案、语义审查、叙事与表达。
适合执行验证：算法小实例、媒体实际播放、输出在目标工具中打开。
适合用户：合同约定的主观偏好、无法推断的关键目标、授权。

**组合子技能时只拥有协调缺口。** 例如某参数影响两个子组件，父技能解析一次，传给双方，检查实际输出遵守它。不要复制子技能的私有实现来获得“更简单的路径”，也不要把子技能自己的安装/确认惯例当作覆盖用户已有授权的新要求。

外部依赖失效时，替代路径必须保留任务所需的质量与安全条件；无法保留则如实停止对应部分，不借降级绕过验收。

## 5. 为真实消费设计数据，不为抽象设计数据

每个产物指出生产者、消费者、内容标准和更新方式。

- 短文本只给用户看：Markdown 往往足够。
- 多步骤读取同一事实：可保存一个小 JSON/Markdown 包，包含来源和未确认项。
- 昂贵提取被多输出使用：复用原始材料、稳定标识和共享索引，消费者各写各的交付目录/文件。
- 大结构有机械字段与创作字段：先生成 skeleton，只让模型填内容；无需重述不可改字段。
- 候选需要有限修改：patch 白名单、必要类型检查、明确可修改例外，再由程序合并；少量普通文案直接编辑更简单。

共享包不自动等于不可变 ledger；原子替换一个文件不等于多文件事务。只有旧结果可能误配或某次接受需要重建时，才添加输入指纹、generation marker 或版本绑定，并确定消费者在哪里校验。

输入变化后，标记/重建依赖它的输出，保留无关昂贵结果和用户修改。没有检测或确认输入关系，就不能宣称缓存有效。一次运行的临时失败不应破坏上次可用交付。

## 6. 在有需要时加入导航与恢复

当阶段多、分支多或中断恢复确实困难时，再设计 navigator。

它需要回答：
- 哪些文件/内容是当前阶段事实？
- 哪些输出存在但无效或不适用于当前输入？
- 下一动作的执行者、输入、输出和所需检查是什么？
- 重复询问下一步是否会引起副作用？
- 什么条件算完成、部分完成、待输入或无法完成？

人读文本或机器 JSON 都可以；选一种与宿主真实能力一致的协议。让协议与实现一起交付，不创造未实现的 exit codes、CLI flags 或“通用 executor”。

确定性检查失败时，路由必须真的执行合同中的行为。若验收是严格的，不能在重试耗尽时把失败改成成功；若合同允许带 caveat 交付，状态与用户答复都需保留限制。不要用空文件、只有 status=passed 的自报 JSON 或退出码 0 作为唯一成功证明。

固定顺序和少量分支用普通代码；简单恢复加必要状态文件即可。只有跨会话等待、多分支协调和恢复逻辑确实值得时才评估 LangGraph，不按节点数量选框架。

如已使用具有持久化/重试能力的 runtime，复用它；不要再堆一套重复控制面。反过来，仅为本地长任务恢复也不必先部署 workflow server。

## 7. 失败分类与修复范围

| 失败 | 合理行为 |
| --- | --- |
| 瞬时网络/限流 | 有限重试或其他可用来源；记录未覆盖项，别当成“零结果” |
| 输入/格式不合法 | 明确修复目标，保留原文，限制重复尝试 |
| 语义不成立 | 给具体 finding、证据和下一次改变的约束；没新信息则停止或弃权 |
| 不可修复的方案问题 | 回到有权改方案的阶段；检查者不擅自重新设计 |
| 关键预算/权限/目标缺失 | 仅暂停依赖项，请求必要信息，继续独立工作 |
| 一个输出分支失败 | 按合同决定整体失败或明确部分交付；不掩盖失败，也不盲目重跑成功分支 |

重试依据至少包含“失败理由、与前次相比的新证据/条件、剩余上限”。去重不能仅比较随意分配的 lesson_id；至少绑定同一 finding 或来源，语义近似需诚实判断。上限按任务成本设置，ResearchStudio 的 3+1 不具有普适性。

多 worker 竞争、外部写入和重复发送若是实际需求，要设计对应的去重/并发与授权机制；不是实际需求就不加锁、队列或 lease。

## 8. 先验收再整理 Skill

先验证最短完整路径能生成可消费产物。随后选一到几个最可能出错的边界，参考 [验收案例](acceptance-cases.md)；有不变量的逻辑留下可运行检查。

- 代码检查：字段和路径、坏输入、依赖失效、恢复或关键分支；
- 内容检查：来源、约束、质量标准与不确定性；
- 集成检查：下游真的接受结果，公共参数未被覆盖，最终文件可用；
- 行为检查：换一个 Agent/上下文能否按 Skill 做对，简单任务是否仍保持简单。

将发现的失败修在责任所在处；不要每遇到一个反例就向入口增加一条永久通用规则。

最后把稳定的操作合同写进 SKILL.md，按需把细节拆到 references。不要为演示新方法交付无法运行的伪命令、空脚本或“以后实现”的自动化。未做的端到端测试必须在交付中说明。

## 9. 先保质量，再测实际成本

重构用同组成功例、结构变化例和缺材料例核对原合同：完整性、事实/证据、用户约束和下游可用性不能因调用变少而降低。旧版未运行就明确写未测，不把文档承诺当基线结果。

按 [验收方法](acceptance-cases.md) 记录实测耗时、代码重写次数、全部可观测模型调用与 token、修复次数和维护投入。冷/热条件分开，不可观测项记 unavailable，不能以文件数量或估计 token 宣布收益。
