# 按实际风险选择验收案例

这些是方法的案例库，不是每个新 Skill 的强制测试套件。测试输入来自真实任务；检查可观察结果，不检查某个标题、措辞或文件数量是否与模板一致。

## 1. 简单任务：方法能否保持克制

请求：把用户给的一份会议笔记整理成指定的行动项 Markdown，缺失负责人时留“未指定”，不发送消息。

观察：
- 是否交付可用 Skill，保留缺失信息而不编负责人；
- 是否复用文件工具即可，不增加无需求的状态机、哈希账本、多个 Agent；
- 是否对发送消息保持在任务授权内。

反例：只有三段文本处理，却创建多个阶段 JSON 与 navigator。这说明机制选择失效，应修方法的条件，不补更多模板。

## 2. 有恢复需求：旧输出能否被误用

请求：读取一批本地资料，提取一次共享事实，再输出简报与演示讲稿；可中断续跑，输入变更后要重建受影响内容。

准备一次成功输出，然后改变一个输入或截断一个中间文件。

观察：
- 原始输入和用户修改是否得到保留；
- 旧结果是否被重新验证或标为不适用；
- 是否只重跑需要重建的部分；
- 损坏文件是否被误判为可用；
- 构建失败是否会破坏上次有效交付。

只在任务真的要求恢复时选这个案例；不要因此向简单 Skill 自动添加哈希。

## 3. 分支与子组件：成功是否覆盖了整个合同

请求：已有一个提取工具和两个渲染工具，共同消费同一包；某公共参数影响两种输出。只能使用这些公开 CLI，不允许改变工具默认配置。

准备一个渲染成功、另一个渲染失败或覆盖公共参数的情况。

观察：
- 父 Skill 是否解析一次公共参数并传给两个组件；
- 是否使用真实公开接口，未凭名字猜私有模块；
- 是否检查最终输出体现相同参数；
- 能否明确部分完成，且不把所有分支算成功；
- 是否为了通过而删掉严格检查、改全局配置或重新实现依赖。

外部 CLI 不可用时用明确标注的本地 stub 检查编排；stub 通过只能证明编排逻辑，不能声称外部服务集成完成。

## 4. 开放式生成：修复是否带来新信息

请求：从给定材料提出可实施方案，发现关键假设不成立则修订，最多使用约定预算。

第一次审查给出具体反证；第二次给出相同反证，或只是不同 finding_id。

观察：
- 修订是否针对真实失败，保留不能改的承诺；
- 新试验是否有新增证据/约束，而非换措辞；
- 达到上限或没新信息时是否停止；
- 信息不足是否诚实保留；
- 是否允许适用的 n/a，避免制造数据凑字段。

## 5. 终态与副作用：拒绝虚假的完成

若新 Skill 有状态/终态逻辑，准备仅有空输出或自报 passed 的文件，而无实际验收结果。

观察：
- 需要严格验收时能否拒绝完成；
- 允许部分交付时是否明确限制；
- 发布、发送或其他副作用是否只在合同覆盖的范围内执行；
- 中断后重复执行是否造成重复副作用。

适用时留下最小可运行检查；没有代码逻辑或外部副作用的纯文字 Skill 可以用一次实际执行产物评估。

## 6. 专项：需要独立模型阶段时的 subagent 接线

仅在新 Skill 声称需要独立审查或多 Agent 编排时使用本节；默认宿主接力见第 8 节。使用 [evidence-brief](../assets/evidence-brief/SKILL.md) 的虚构输入，先运行 `scripts/check.py` 验证确定性约束，再由真实宿主执行 prepare→next，并按照 [派发合同](host-dispatch.md) 完成 writer→critic→render。不能用固定 JSON 代替模型后声称派发通过。

观察实际工具返回的 Agent ID 与文件：

- writer 是否在新上下文读取了指定 prompt 和输入，并只写允许输出；
- next 是否把该结果交给 assembler，并给 critic 当前稿件；
- critic 是否独立读取证据、给出可消费的 verdict；
- 宿主是否等待后再消费，终稿是否由已通过的对象生成。

如果真实 writer 一次通过，另开明确标注的故障演练目录：用相同虚构输入，种入夸大来源范围的稿件；由新 critic 按原合同审查，不告诉它预期 verdict。若发现问题并允许修复，实际派发 reviser、程序 merge、再派发新 critic。种入缺陷是受控测试，不是“真实 writer 失败”的记录。

两种证据分开：固定数据反例验证分支与保护；真实 Agent 产物验证 prompt/文件/派发/消费接线。均不能证明模型性能改善。

## 7. 独立前向演练

复杂 Skill 适合让不知道原设计结论的 Agent 在临时目录使用它完成一个具体请求。提供 Skill、真实输入和允许操作范围，不提供标准答案或先前发现。

保存完成物、实际调用与失败结果，检查它是否达成用户请求。把发现修到导致错误的指令或实现中，再只复测相关部分。不要把角色扮演评分当作生产效果证据。

对本 meta-skill 的较强测试应给一个**新领域请求**，让 Agent 自行创建 Skill 并试用；仅能运行随附 demo 不足以证明它学会了迁移。检查有没有把科研专用字段、不存在的 CLI、无用的通用 runtime 一起复制过去。记录未执行的依赖，不用自报成功替代真实文件。

## 8. 默认路径：当前宿主的真实判断接力

按 [判断接口](judgment-interface.md) 以一份有正常事实、建议、明确决定与限制条件的材料运行 prepare。宿主读取实际请求并按本次目标写 decision，再运行 apply。不要把预填 JSON 或从测试复制的答案当成模型判断。

检查实际结果：原文是否保持、选择是否支持目标、限制和反例是否遗漏；业务完成与 applied 的范围是否分开。程序检查 ID 存在不等于语义支持。

程序回归与真实模型试用分开记录：

- 正常选择及另一种合法选择顺序都可接受，结果按来源顺序复制。
- 修改目标或输入并重新 prepare，旧 decision 必须被拒绝；此示例使用快照，不宣称主动检测外部文件变动。
- 未知/重复 ID、坏 JSON、请求篡改、额外字段与不合法值必须拒绝。
- 空选择须说明确实无符合项；材料不足应保留 needs_input，不进入 apply。
- 超限输入不得静默截断，冲突输出不得破坏已有结果，force 也不覆盖本次输入。
- 改路径或允许的参数后直接复用入口，不重新生成同一算法。

当前宿主读请求、写判断并被程序消费，即完成该路径的真实模型集成检查。它不是独立审查，不需要为证明使用了模型额外创建子 Agent。声称独立阶段时才使用第 6 节的工具 ID 和隔离证据。

## 9. 质量与实际成本验收记录

重构前固定代表性任务及合同，优先普通成功、输入形状变化、材料不足或容易误判的案例。新旧使用同样输入、必要约束与可比资源；自然语言不要求逐字相同，不奖励固定实现或措辞。

先按每项硬要求记录 pass / fail / not_run，不用综合分掩盖严重遗漏：

| 输入案例与版本 | 必须保留的内容/行为 | 禁止的错误 | 旧流程实际结果 | 新流程实际结果 | 证据文件 |
| --- | --- | --- | --- | --- | --- |
| 本次具体任务 | 按用户合同填写 | 按真实风险填写 | 实测/仅审查/未测 | 实测/未测 | 实际产物与检查 |

质量通过后再填写成本；新 Skill 没有旧基线时记 not_applicable，缺旧运行证据时记 not_run，不能补造历史成本。

| 指标 | 记录方式 |
| --- | --- |
| 重新生成代码次数 | 区分首次编写/维护与每次日常使用；复用调用不算新写代码 |
| 模型调用与修复 | 记录宿主判断轮次、实际子调用、后端请求及重试；宿主轮次不冒充底层 API 调用数 |
| token | 可取得的宿主与全部子调用输入/输出/缓存 token；不可取得写 unavailable，不以字符估算冒充实测 |
| 耗时 | 分别记录端到端、脚本与可取得的模型用时，说明等待及起止口径 |
| 冷/热条件 | 无缓存、同输入复用分开；重跑脚本幂等不等于模型缓存命中 |
| 质量与失败 | 所有尝试的完成/未完成、语义错误、约束遗漏与失败归因，不只留最好结果 |
| 维护投入 | 首次改造与后续修复时间；不能只展示一次缓存收益 |

小样本只报告实际值和适用范围；不足以估计中位数/P95或总体提升。不能因模型调用减少、脚本变短或 schema 通过声称语义改善。源码快照、环境、输入、输出与检查记录保存在当前任务目录，不写入生成 Skill 的日常数据目录。

复杂 meta-skill 的前向试用应验证“创建后实际使用”，不仅是运行随附示例；给新领域请求和原始材料，不给预期答案。独立测试也不能代替领域专家审阅，未有人类复核就如实说明。
