# 已有工作流的执行边界审计

用于“已经脚本化过，但仍慢、不稳定、重复消耗 token”的维护。不要据此为短任务增加状态机、模型调用或多 Agent。

## 根因：有能力不等于默认路径使用了能力

PaperFlow 的 Brief 曾经移走原文抄写，加入分块保存和字段修复；但默认路径仍由通用模型循环决定读取、翻页、保存、装配和返修。模型每轮还收到完整工具集合与历史。局部组件测试通过，不能证明端到端执行权或上下文结构已改变。

可迁移的教训是同时检查五个方面，而不是只看输出 schema：

| 层 | 需要核实的事实 | 常见假完成 |
| --- | --- | --- |
| 数据处理 | 原文、路径、编号、已确认事实究竟由谁复制 | 新增函数，但仍让模型生成完整对象 |
| 流程调度 | 谁依据前一步结果确定下一步，是否需要额外模型回合 | 提示词要求优先调用脚本，就称程序编排 |
| 上下文准备 | 实际每次请求携带哪些 schema、源文、历史和失败信息 | 输出分块了，但输入仍反复携带整套上下文 |
| 失败恢复 | 如何定位继续位置、验证旧结果、判断依赖失效 | 文件保存了，但恢复后模型仍从头阅读和猜测 |
| 要求履行 | 用户批准的每项要求是否贯穿任务、产物、证据和最终验收 | 数量够了、文件存在或 worker completed，就宣布计划完成 |

## 审计方法

1. 从用户实际入口追踪到模型适配器、工具执行和最终消费者。查看默认配置与路由，不能只调用新函数测试。
2. 将下一步分成两类：需要新增语义判断，或现有状态足以决定。后者包括分页、状态检查、写入、关系映射、固定装配和确定性校验，应直接执行。
3. 检查模型收到的真实请求，包括宿主/CLI 包装、工具定义、源文重复和历史增长。字节数、token、缓存命中和计费单位分开记录，不用字节估算冒充实际用量。
裁剪上下文必须保留当前判断所需的完整契约。例如字段返修工具虽然接受 `value: object`，仍须向模型提供目标字段的实际 schema（含必填子字段、类型、范围与未知值规则）；只有字段路径和错误文本会迫使模型重新猜结构。无效补丁只允许修正补丁，不得自动升级为重写整个有效对象。

4. 从下游产物反查剩余的抄写：引用、模板、列表索引、编号、用户约束及版本绑定。模型选择稳定 ID 或小范围变更，程序保留原字节；有歧义时返回需要判断，不擅自猜事实。
5. 检查失败发生在什么层。结构错误局部修补且有效字段不漂移；语义错误交回对应判断；输入/权限缺失保留 needs_input；传输与未知错误保留诊断，不假装是研究判断错误。
6. 用输入依赖、规则版本、来源完整性确定缓存是否适用。跨修订复用要重新验证绑定，不直接复用旧证据 ID。保存成功结果不自动赋予它审批或验收权。

固定顺序优先普通函数。已有控制平面时在其内部完善执行边界，避免增加第二套通用引擎。研究、法律等领域判断仍需语义判断，不能通过删除证据要求或强造默认值降低成本。

若涉及批准计划和后续创作，继续执行 [要求闭环审计](obligation-closure.md)。阶段内优化不能代替端到端要求覆盖；动态任务应输出受约束的数据并由已有执行器调度，参数接口必须提供真实 schema。

## 验收要能反驳“只是多了一组工具”

按影响选择最少的有效检查：

- 真实默认入口是否直接执行机械步骤；没有让模型重新选择新旧接口。
- 改变任务输入后，阶段请求是否只包含其相关材料和 schema；是否出现未声明截断或无界聚合。
- 关键步骤失败或进程重启后，已验证的无关结果是否复用；改变依赖后旧判断是否失效。
- 字段修复前后有效主张、数据、资源判断是否保持不变。
- 原合同的证据、权限、范围与最终验收是否仍有效。
- 用已有真实任务接真实模型，记录全部尝试，包括失败与未知用量；分清软件夹具、真实研究输入、内容审查与完整交付。

不要用模拟模型直接返回理想答案证明稳定性，也不要为追求“一次成功”降低科学校验。若没有同任务同模型的旧版对照，就报告新版实测和历史边界，不宣布性能提升比例。
