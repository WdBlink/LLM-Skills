# Workflow Skill Creator

交付另一个 Agent 能实际执行的 Skill。不是只列“模块化、隔离、校验”的原则：要把 **谁调用脚本、谁创建子 Agent、哪个 prompt 在何时加载、文件由谁写又由谁读、失败怎么回到流程** 接成一条可运行链。

用户只要分析时交分析；要求创建或修订时完成文件与验证，不停在设计建议。生成的 Skill 直接说明用途、输入输出、执行步骤和限制，不附带“借鉴了谁”“采用某项目设计模式”等设计来源介绍。领域证据引用与必要的许可证声明照常保留。

## 默认必读：源码到实现的十个步骤

调用本 Skill 即表示采用 [源码到实现的十个步骤](references/implementation-walkthrough.md) 及其设计模式。开始设计或修改前先读取该文，并用它组织任务追踪、产物合同、程序/模型/宿主分工、文件交接、失败恢复与运行验证。同一会话已读且内容未变时可复用，不必重复加载。

默认采用上述方法，再按实际任务裁剪实现规模：短线性文稿转换可能只需 SKILL.md，不因此跳过十步法的阅读与设计判断；也不为凑节点强加脚本或多个 Agent。包含多阶段模型编排的复杂请求还必须读派发、prompt 两份参考并落实相关接线；不要把可运行样例降格成可有可无的附录。

## 1. 追清一个真实任务

读取现有 Skill、受影响脚本、调用方与已安装工具的真实接口。有参考仓库则固定版本，沿入口→中间文件→消费者→失败分支追一次。区分已实现行为、文档合同与本地建议。

把用户给什么、拿走什么、质量依据、不可改变的事实/限制、写入与外部动作范围写清。领域知识必须进入具体判断：研究审查要有文献/失败教训，证据简报要检查来源范围和冲突；只增加 Agent 角色不能补上领域依据。

## 2. 先画产物合同，再写 prompt

对每个必要阶段写一行：`输入视图 → 程序或模型动作 → 输出字段/文件 → 消费者 → 校验与失败去向`。

- 程序负责解析、切片、查表、join/group、字段保护、合并、渲染和可判定的不变量。
- 模型负责解释、生成与语义审查；输出消费者需要的增量，避免重述大对象。
- 宿主负责实际工具调用、创建/等待子 Agent、处理握手与回到导航；脚本打印“派发”不算真正执行。
- 同侧创作步骤可共用上下文；作者与 critic、critic 与 reviser 在需要独立判断时分开。阶段由责任与依赖决定，不按每个动词拆 Agent。

## 3. 实现最短完整链

按任务裁剪以下执行骨架：

```text
prepare → skeleton → writer(fill_map) → assemble
                                      ↓
                                fresh critic
                        advance / revise / abandon
                       render    patch       blocked
                                  ↓
                                merge → fresh recheck → render / blocked
```

这是随附样例的结构，不要求每个新 Skill 都采用全部节点。创建新领域 Skill 时先替换输入、质量标准和输出，再保留真正需要的节点。

脚本优先标准库和现有工具。一个小 `run.py` 可以同时容纳命令与只读 next；有独立复用/维护边界才拆 helper。路径基于 Skill 自身位置，外部子进程用合法参数数组、明确工作目录与超时，检查实际输出。

对大结构采用 skeleton/fill；对受限修改采用 patch/merger。把来源事实和用户承诺留给程序复制，明确允许修改的字段。保留必要类型/非空/来源 ID 检查；不能仅靠 prompt 写“不得修改”。

## 4. 接上宿主和 prompt

导航每次给完整动作：执行者、准备动作、prompt 路径、必读/按需输入、精确输出、返回信号和下一步。选文本或 JSON 中一种已实现协议；使用文本协议时，保留多行 INPUT/RUN 与 NOTES。

按 [宿主例](references/host-dispatch.md) 实际使用可用的 subagent 工具：新上下文、只给阶段路径与合同、明确写入责任、等待完成，再由程序消费文件。没有真实独立调用能力时说明降级，不能编造 SDK、CLI 或 dispatch receipt。

阶段 prompt 先定义输出与可修改范围，再定义领域动作和必读证据。稳定规则放文件，本次候选/重试 findings 放输入；准备阶段先产出消费视图。`system-prompts` 是文件命名，`<<SYSTEM>>` 是文本分隔符，都不会自动提高消息优先级。

并行仅用于可独立推进且写目标分开的动作。输入可能被另一分支修改时，要么串行，要么记录实际消费字段并在汇合时检查、失效重跑。

## 5. 让失败路径也能执行

程序输出损坏、模型内容不成立、工具暂时失败与缺关键输入分别处理。语义修订需具体 findings 与改动范围；重试给新增约束而不是“再生成一次”。上限按实际成本确定，耗尽后诚实 blocked/部分交付，不自动改成成功。

有导航就保持 next 只读，重跑同一动作可预测；明确输入变化如何处理。小样例可拒绝复用不同输入的 run 目录，不必立即引入缓存框架。实际存在并发提交/事务需求时再使用现成 runtime。

## 6. 用实际执行检验接线，再打包

按 [验收方法](references/acceptance-cases.md) 选择最小检查：

- frontmatter、资源链接、命令参数与安装后路径正确；使用可用的通用 skill-creator 格式验证器。
- 非平凡程序逻辑留一项能捕获错误的可运行检查；关键保护做越权 patch、坏 JSON 或失败终态反例。
- 含模型阶段时，至少实际派发一次，让子 Agent 读 prompt、写产物，由后续程序消费；不能拿纯 JSON→Markdown 测试替代。
- 足够复杂且允许委派时，用新 Agent 和新请求做独立前向创建/使用测试；核对实际文件，不提供预期结论。
- 需要隔离、修订或多产物的保证分别核验；运行记录区分真实模型、确定性 fixture、外部服务与未测路径。

尊重用户指定安装位置，保留自动发现与已有 UI/权限字段。SKILL.md 放入口和关键规则，长方法放 references，用于复制/改造的可运行模板放 assets；复制上游代码时保留许可证。交付 Skill 路径、具体新增能力、实际验证与重要限制。不要以 prompt 变长、代码减少或测试数量推断模型质量提升。
