# 把设计落实到运行行为

## 从一份能交付的结果倒推

选真实请求，记录输入和授权范围。对每个必交项写出「谁需要 → 具体内容 → 由什么材料产生 → 在哪里使用 → 谁用什么办法验收」。简单任务几行就够。多个义务容易混淆时，用稳定标识贯穿计划、产物和最终检查。允许执行方式随新证据调整，保留用户已约定的结果与质量标准。目标确有变化时，记录用户的改动及受影响的义务。

例如，用户要一份可打印的双语说明书。把两种语言的正文与对应版本、必含章节和最终打印件关联，再据此安排译写、校对和排版。只数 PDF 数量会放过“两份内容相同的中文版”。据此可以在编写流程前就设计一个有区分力的反例。

## 选择会改变下一步的条件

| 实际问题 | 写进技能的行为 |
|---|---|
| 一次读取或转换即可交付 | 直接产生输出并检验，无需轮次、台账或评审角色。 |
| 有多类事项或互相依赖的产物 | 按意图选主流程，按当前有效产物选阶段。例如同一事项已有校对件时先核对其对应版本。附加领域只负责它能解决的问题。 |
| 有明确可改范围、可逆候选和可复测指标 | 记录基线、指标方向、验证方法和硬约束。每轮做一项可解释的变化，验证后保留或回退并记录原因。评价器、验收样本和历史结果在候选修改范围之外。 |
| 探索指标可能奖励错误行为 | 指标用于比较候选，最终验收另查真实质量。例如缩小图像后仍须读出原图细节。无有效测量时记录原因；保留可解释的负面结果。主观质量用具体证据或审阅判断。 |
| 多条探索路线共享同一基线，且能独立比较 | 可按资源和授权隔离比较，保留每条尝试的证据。胜出的候选交回主流程，继续履行其余义务。 |

## 确定模块怎样协作

为确实需要单独运行或返工的阶段写清 **进入证据、读取材料、可执行动作、返回产物、验收者、后继或返工位置**。主流程持有任务范围与整体完成条件。局部协议可以调研、诊断、试验或修订，在约定范围内返回判断及证据。只在有状态的工作流里确定一个状态维护者；证据接收、回退和恢复共用同一套判断。规则明确的检查尽量放到真实提交或交付入口。

渐进式披露有两层。Codex 通过主技能描述识别适用请求；执行时根据已接收的产物，提供当前阶段的规则、证据、允许动作和预期输出。把全套资料拆成文件后仍在启动时全部读取，会失去第二层的作用。重开会话时，先查看现有产物及其版本，再决定从哪一步继续。

## 材料、人工交接和外部操作

- 引用附件或模板的来源，追到实际可用的文件，核对版本、字段和适用条件。检索索引或 OCR 用于定位，关键条款回到原件。正式资料相互冲突时查修订关系，缺失的材料明确列出。
- 区分查询、准备和实际办理。用工作副本填有来源的字段，保留签字位、公式和版式。需要签字时交付可打印件、标明位置，记录等待条件。回传后核对事项、版本和完整性，再恢复依赖步骤。
- 仅当目标流程需要人工选择时，列出角色或候选，以及决定将作用于哪个对象。具体人选、承诺和额外授权以用户真实回答为依据，已有明确回答可复用。
- 为实际外部动作定义成功证据。草稿、已提交和已获准有各自的证据。提交时若连接中断，先检查回执或服务端记录，确认结果后再决定是否重试。等待期间继续独立且已授权的工作。

## 怎样发现流程偏移

从同一入口跑一个正例，并根据实际风险选反例。删除必交项、用内容错误的文件补足数量、在审阅后改动上游材料，分别检查默认交付路径会不会报告缺项或要求重新核验。失败应回到能修复该项的步骤，继续复用有效的独立成果。涉及恢复时，换一个干净会话，只给原请求、技能和工作目录，检查能否找回已完成事项及下一步。

最后核对 Codex 的实际发现和调用、输出是否进入下游，以及已知缺口。脚本测试、宿主真实运行和外部业务完成分别按实际证据记录。
