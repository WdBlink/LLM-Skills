# 从 AutoResearch 创建新技能

为用户交付能从 Codex 单一入口使用的领域 Skill。AutoResearch 提供开发起点，目标任务决定保留、改写、替换或删除哪些代码。

## 判断是否进入

| 用户的目标 | 动作 |
|---|---|
| “照 AutoResearch 的做法给我做一个设备验收 Skill” | 进入本流程。前文已经约定这种做法时沿用。 |
| “把设备手册整理成技能，按设备类型拆模块” | 走普通技能创建。多模块、自动化、科研或渐进式披露本身不触发本流程。 |
| “用 AutoResearch 研究这个问题” | 交给已有 AutoResearch。 |
| “这个领域技能适合仿照 AutoResearch 吗？先给方案” | 先回答设计问题。用户要求实施后再建立副本。 |

## 完整克隆，再动手改

每创建一套新技能，先在技能发现目录之外选定一个新的开发目录。优先用用户指定的位置。从**本创建器目录**调用脚本，将开发目录换成实际目标。以下示例使用默认的个人安装位置。

```sh
python3 ~/.codex/skills/autoresearch-skill-creator/scripts/clone_base.py ~/projects/equipment-acceptance
```

脚本完整克隆 `https://github.com/uditgoenka/autoresearch.git`、校验起始提交并保留 Git 历史，以 `refs/autoresearch/base` 记录基线。第一版默认使用上游提交 `7bddd056dfd0b0ded8360588d8101b1ecb5c0baa`。用户指定其他版本时，查明其完整提交 SHA，传入 `--revision SHA`。已有任务续办时核对工作区、上游、基线与现有改动，接着做。克隆中断时先检查该目录的具体状态，保护已有文件。

在这个副本里直接改实际入口、协议、脚本、路由、工具和测试。先追踪一次所选 Codex 入口及其生成来源，确定以后维护哪一份。若沿用上游生成脚本，同步修改其输入和打包逻辑，避免重新生成时还原旧名称或旧行为。源码和分发包保留适用的版权与许可。上游组件的保留数量没有下限。

## 从交付反推工作流

改入口前，取一个真实请求，写清用户会拿走的结果、实际使用者，以及怎样知道结果可用。复杂任务先读[工作流设计与验收](references/workflow-design.md)，沿同一份设计完成以下工作。

1. 把必交项对应到产物、依据和验收动作。从下游所需的产物向前找依赖，据此决定哪些步骤应该独立，哪些可以一次完成。
2. 让主入口根据意图和已有证据选择当前动作。领域说明与局部协议写成普通 Markdown，按需读取。需要跨阶段交接时，给下一步真实输入、可用工具、完成条件及失败出口。
3. 把可重复的机械操作接到已有工具或小脚本。领域判断由宿主依据实际材料完成。需要人决定的事项绑定到具体请求，仅暂停依赖该决定的动作。
4. 用一条能产生最终结果的路径从头做到尾，再补充目标范围内的其他分支。按实际目标选择一次性处理、分阶段推进或可复测的迭代。上游的固定轮数、命令、角色、目录和状态引擎均可改写或移除。

## 交付前走一次真实入口

- 从目标技能的主入口给出一项代表性请求，实际打开或消费输出。再构造一个会导致假完成的反例，观察默认流程是否拦住它；修复后重跑受影响部分。
- 有等待、重试或外部动作时，另验证恢复位置、版本变化和回执处理。用测试资源演练外部动作，报告演练边界。
- 对仍有用途的上游行为运行相应回归，已替换的行为按新目标验收。用 `git status --short` 和 `git diff refs/autoresearch/base` 核对实际改动及新增文件。
- 安装时只交付目标包，包内只设一个顶层 `SKILL.md`。核对相对引用和脚本依赖，从开发目录之外调用，并用 Codex 技能列表重扫确认该包只有目标入口。交付开发路径、安装路径、基线与实际验证结果。
