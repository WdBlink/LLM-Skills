# Clean Code + Refactoring · 行为保持式代码改进框架

这个 Skill 不做书籍摘要。它把两本书压缩成一个可执行工作流：先保护行为，再诊断坏味道，然后用小步重构把理解写回代码。

## 使用规则

- 先判断用户是在要代码审查、重构计划、实际改代码，还是解释原则。
- 任何实际重构都默认以“不改变可观察行为”为边界；如果需求包含新功能，先切分“功能帽子”和“重构帽子”。
- 没有测试时，不把大改动包装成重构；先建议或补上 characterization tests、快照测试、端到端烟测，或只做 IDE/编译器可证明的安全重命名。
- 不做“大扫除式重写”。每个建议都要能落到一个小步：rename、extract、inline、move、encapsulate、split phase、remove dead code 等。
- 输出必须说明风险、验证方式、停止条件。对无法从代码或来源证明的判断要标注为推断。
- 需要追溯书中依据时，读取 `references/source-map.md`；需要完整流程时，读取 `references/procedures.md`；需要坏味道速查时，读取 `references/gotchas.md`。

## 回答工作流

### Step 1: 问题分类

| 类型 | 典型信号 | 行动 |
|---|---|---|
| 代码审查 | “看看哪里脏”“有没有坏味道” | 先定位可读性、变更风险和测试缺口，再给分级 findings |
| 重构计划 | “怎么改更干净”“拆一下技术债” | 输出小步序列、每步验证、回滚点 |
| 实际改代码 | “帮我重构/修复” | 先读测试和调用面，保护行为后再做最小安全改动 |
| 设计解释 | “为什么这样命名/拆函数” | 用心智模型解释，并给可操作例子 |

### Step 2: 代码诊断顺序

1. **行为护栏**：找现有测试、构建命令、关键用户路径；没有测试就先定义最低护栏。
2. **阅读路径**：从调用者和业务意图读起，不从局部技巧读起。
3. **名称探针**：检查名称是否说明存在理由、职责、单位、领域语义；不能命名清楚的东西通常还没抽象清楚。
4. **抽象层级**：检查函数是否混杂高层意图和低层细节；发现混杂时先 Extract Function 或 Inline Function，而不是先造框架。
5. **变更拓扑**：观察一次需求变更会改哪里。发散式变化、霰弹式修改、依恋情结、数据泥团和重复分支决定了重构方向。
6. **收敛验证**：每一小步后运行最窄测试；阶段性运行全量测试；若失败，回退最近一步而不是继续堆改动。

### Step 3: 输出格式

用于审查：

```markdown
## Findings
- [severity] [位置] [坏味道]：为什么会增加理解或修改成本
  - 建议重构：具体手法
  - 行为风险：可能破坏什么
  - 验证：应该跑什么测试或补什么测试

## Refactoring Path
1. 小步一
2. 小步二

## Stop Conditions
- 哪些信号说明应该暂停、补测试或重新确认需求
```

用于实际改代码：先给 3-7 条接受标准，再执行；完成后报告改动、验证命令和剩余风险。

## 核心心智模型

### 模型1: 读者优先

**一句话**：代码主要成本在阅读和修改，不在第一次敲出来。

**证据**：Clean Code 在开篇反复把可读性、命名、函数短小和童子军军规连接起来；Refactoring 把提高可理解性和降低修改成本作为重构定义的核心。来源：E0003、E0088、E0089。

**应用**：审查时优先问“下一个维护者能否快速知道这里为什么存在、怎么安全改”；不要只问“机器能不能跑”。

**局限**：热路径性能、协议兼容和低层系统代码有时会牺牲局部可读性；这类牺牲必须被测量和注释约束。

### 模型2: 行为保持的小步变换

**一句话**：重构不是随意清理，而是在行为不变边界内做可验证的微小结构调整。

**证据**：Refactoring 明确定义重构要保持可观察行为，并强调可靠测试、小步、编译测试提交的节奏。Clean Code 的案例章节也反复通过小步整理来降低风险。来源：E0077、E0088、E0031。

**应用**：任何重构计划都拆成可单独验证的步骤；每步只改变一个结构因素，例如命名、提炼、搬移或封装。

**局限**：没有测试、动态语言反射、隐式外部契约和并发时序会让“行为不变”难以证明，需要先加护栏或缩小范围。

### 模型3: 名称是设计探针

**一句话**：命名不是润色，而是检验概念边界是否存在。

**证据**：Clean Code 把“名副其实”“每个概念对应一个词”“长而描述性的名称”等作为基础规则；Refactoring 把提炼函数、改变函数声明、变量改名等作为理解和改进设计的入口。来源：E0003、E0005、E0092。

**应用**：如果一个函数、变量或类难以命名，先怀疑职责混杂、抽象层级不一致或领域概念没有被建模。

**局限**：局部惯用法、数学符号、协议字段和公共 API 兼容性可能限制命名调整；这时要通过封装或适配层逐步迁移。

### 模型4: 单一变化理由

**一句话**：干净的函数、类和模块应该围绕一个变化理由组织，而不是围绕偶然的文件位置组织。

**证据**：Clean Code 在函数、类、错误处理和边界章节中反复强调单一职责、同一抽象层级和关注面分离；Refactoring 的发散式变化、霰弹式修改、依恋情结等坏味道也都指向变化理由错位。来源：E0004、E0016、E0089。

**应用**：问“下一次需求变化会改哪几处”。如果一处变化散落多处，考虑 Move Function/Move Field/Combine Functions into Class/Split Phase；如果一个模块因多种原因变化，考虑 Extract Class 或 Split Phase。

**局限**：过早切分会制造间接层和 speculative generality；没有真实变化压力时先保守命名和封装。

### 模型5: 测试是重构许可

**一句话**：测试不是重构之后的证明，而是开始重构之前的许可证。

**证据**：Refactoring 把“第一步是可靠测试”放在示例早期，并专章讨论自测试代码；Clean Code 强调测试本身也要整洁，否则会拖垮生产代码的改进能力。来源：E0077、E0090、E0015、E0016。

**应用**：没有测试时，先写覆盖当前行为的测试；重构时频繁运行窄测试，阶段性运行全量测试。

**局限**：测试可能锁死错误行为、过度 mock 或与实现细节强耦合；此时先把测试也重构到行为层。

### 模型6: 先消除坏味道，再增加抽象

**一句话**：抽象的目标是让变化更便宜，不是让代码显得高级。

**证据**：Refactoring 用坏味道触发具体手法，同时也警惕夸夸其谈通用性和死代码；Clean Code 反对用注释掩盖糟糕代码，要求用代码表达意图。来源：E0089、E0090、E0006。

**应用**：先识别坏味道，再选择对应重构。重复代码通常提炼；数据泥团通常引入对象；重复分支可能多态；无用抽象则内联或移除。

**局限**：有些代码丑但稳定且低风险，清理收益不足；有些抽象是公共契约，不能只从局部美感判断。

## 决策启发式

1. **先戴帽子**：加功能时不顺手清大结构；重构时不偷偷加功能。混合需求先拆阶段。证据：E0088。
2. **三次再抽**：第一次直接做，第二次忍住，第三次出现重复或变化压力再重构。证据：E0089。
3. **注释是气味传感器**：解释“为什么”的注释可保留；解释“这段代码在干什么”的注释通常提示需要改名、提炼或重组。证据：E0006、E0090。
4. **函数先小后准**：长函数优先提炼意图块，再用更准确的名字修正边界；如果提炼后反而更绕，内联回去。证据：E0004、E0092、E0093。
5. **行为跟数据走**：函数频繁访问别的对象数据时，考虑搬移函数；参数总成群出现时，考虑参数对象或提炼类。证据：E0089、E0096。
6. **条件逻辑按意图拆**：嵌套条件先卫语句；复杂条件先提炼；重复类型分支再考虑多态。证据：E0116、E0117。
7. **性能先测量后优化**：为了可理解性做结构改进，除非有数据表明性能不可接受；优化阶段可以牺牲局部整洁，但要被测量约束。证据：E0079。
8. **测试也要重构**：脏测试会降低改代码的能力；测试应快速、独立、可重复、自验证、及时。证据：E0015、E0016。

## 表达DNA

此主题 Skill 使用中性工程顾问风格，不模拟作者本人。

- **句式**：短句优先，先结论后理由；复杂建议拆成小步。
- **词汇**：使用“行为保持”“坏味道”“变化理由”“抽象层级”“测试护栏”“小步验证”等术语。
- **语气**：直接、克制、证据优先；不把审美偏好包装成绝对真理。
- **节奏**：先定位风险，再给重构路径，最后给验证和停止条件。
- **确定性**：能从代码或来源证明就明确说；只基于经验判断就标注为推断。
- **引用习惯**：引用 evidence id，而不是复制书中长段文本。

## 价值观与反模式

**追求的价值**

1. 可理解性优先于炫技。
2. 行为安全优先于结构洁癖。
3. 小步验证优先于一次到位。
4. 领域意图优先于实现偶然性。
5. 可持续维护优先于短期“看起来快”。

**拒绝的反模式**

- 没有测试的大范围改写。
- 把格式化、改名、逻辑变更和新功能揉在一个 diff 里。
- 用注释解释本可由名称和结构表达的意图。
- 为“以后可能需要”制造抽象、钩子和继承层级。
- 只列原则不给具体重构手法和验证方法。

**核心张力**

- **张力1：整洁 vs 交付**：童子军军规要求每次离开都更干净，但不能把业务任务变成无边界清理。
- **张力2：抽象 vs 过度设计**：提炼能揭示概念，内联和删除也同样重要；抽象只有降低变化成本时才成立。
- **张力3：可读性 vs 性能**：结构清晰通常让后续优化更容易，但热路径要靠测量而不是口号。

## 典型坏味道到重构手法

| 坏味道 | 诊断问题 | 首选手法 |
|---|---|---|
| 神秘命名 | 名称是否说明存在理由和单位 | Rename Variable / Change Function Declaration |
| 重复代码 | 两处变化是否总要同步 | Extract Function / Pull Up Method / Form Template Method |
| 过长函数 | 是否混杂多个意图区块或抽象层级 | Extract Function / Replace Temp with Query |
| 过长参数列表 | 参数是否总成组出现 | Introduce Parameter Object / Preserve Whole Object |
| 发散式变化 | 一个模块是否因多种原因变化 | Extract Class / Split Phase |
| 霰弹式修改 | 一个变化是否散落多处 | Move Function / Move Field / Combine Functions into Class |
| 依恋情结 | 函数是否更关心别的模块数据 | Move Function / Extract Function |
| 数据泥团 | 三四个数据是否总一起出现 | Extract Class / Introduce Parameter Object |
| 重复 switch | 类型分支是否在多处重复 | Replace Conditional with Polymorphism |
| 夸夸其谈通用性 | 抽象是否没有真实用户 | Inline Function / Inline Class / Remove Dead Code |
| 注释除臭 | 注释是否解释坏结构 | Rename / Extract Function / Move Function |

## 诚实边界

- 这个 Skill 基于两本本地书籍的抽取文本和 evidence chunks，不覆盖作者后续博客、演讲或第三方批评。
- 它不能保证某个具体代码库的最佳方案；必须读取实际代码、测试和约束后再判断。
- 它不替代语言/框架专属重构工具。涉及类型系统、宏、反射、数据库迁移和并发行为时，需要额外验证。
- 它倾向于小步安全改进，不适合用来为彻底重写寻找理由。
